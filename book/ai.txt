# Wex и реактивность

Разрабатывая приложения, разработчик рано или поздно столкнётся с комплексностью. 
Сперва внезапно появился, скажем, экран продажника. Теперь экран кассира. 
А приложение тем временем одно и тоже, просто усложняется логика вывода.
Напару с усложнением логики вывода, происходит взрыв условных операций под капотом. Что это?
Это когда у вас в ваших if условиях появляются ещё одни ветки if, в них else, и так далее.
Поддерживать становиться невозможно, читать тоже, расширять - ужас, по другому - никак.
Решая проблему "по другому - никак" нам в индустрию постучалась реактивность. Что это? Обьясняю.

# Реактивность

State (стэйт, состояние) - это базовое понятие реактивности и всех реактивных движков. 
Стейт это состояние приложения, его снимок, набор переменных в памяти. Но зачем? 
Что нам мешает создать обычные переменные через `let x = 5`? Ничего. Но мы что-то теряем. Что? Обьясняю. 

## Декларативность 

Когда мы обьявляем переменную вот так нагло и открыто, мы ручаемся что будем её использовать.
Ведь зачем-то она нам нужна, верно? А зачем? Мы говорили про глобальный стейт приложения и реактивность.
Стейт это по сути набор переменных. Таких как `let x = 5`, просто хранящихся определенынм образом 
в определенном месте. Но в отличии от такого обьявления переменной, где мы полно и цельно берём
за неё ответственность, для стейта ответственность не нужна. Он сам механизм-реализатор ответственности.
Так что же он делает? Сейчас расскажу. 

## Стейт 

Возьмем, на примере, Wex. Мою разработку реактивную как аналог и прямой конкурент React.
```js 
$('#app')
  .state({ title: 'Default Title' })
  .mount()
```
Что здесь происходит? Если идти по шагам, то алгоритм следующий:
1. Выбери мне элемент с айдишником app 
2. Проинициализируй ему стейт со свойством title
3. Смонтируйся в выбранный элемент 

Всё. Ничего сложного, и на странице при этом ничего не произошло. Тогда же зачем этот стейт нужен,
если страница осталась всё такой же? Всё дело в шаблонизаторе и в механизме обработки стейта. 
Сейчас расскажу.

## Шаблонизатор

Каждый фронтентд фреймворк имеет собственный шаблонизатор и виртуальный DOM. Виртуальный DOM 
это по сути сборка всего HTML на странице и создание его виртуальной копии в памяти, грубо 
говоря Вы создаёте переменную `x` куда помещаете ASM-дерево всех узлов вашего HTML-документа 
для будущего развёртывания. Например: `x = ['div', 'p', 'span']`. Но зачем? Для шаблонизатора. 

```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>
```
Смотрите внимательно, что здесь происходит. Мы используем тэг template, который буквально 
не отображается в браузере. Он нужен специально, чтобы наш движок создал виртуальный DOM 
из этого участка кода, самостоятельно не удаляя его из вывода браузера, ведь его итак там 
нет благодаря тэгу template. 

Второе, это присвоение этому темплейту уникального айдишника. Если Вы вспомните предыдущий
код, то именно благодаря айдишнику происходит первичная зацепка и выборка элемента: `$('#app')`.

И, наконец, третье - подозрительно непонятный `{{ title }}` в коде. Что это? 
Ради этого, собственно говоря, всё и затевалось. 

## Реактивный шаблонизатор (или реакткивный DOM)

Реактивность это просто слово означающее наибыстрейший. В данном контексте - наибыстрейшее 
обновление данных. Что будет после запуска нашей страницы с кодом? Попробуйте сами!
```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>
<script>
    $('#app')
      .state({ title: 'Default Title' })
      .mount()
</script>
```
Если не хотите ручками играться у себя в браузере, то вывод будет следующим:
```
Default Title
```
Да, вот так просто. Обычный текст на экране без премудростей. Тогда зачем это всё? 

Всё ради реактивности. А именно: когда мы обновим наш стейт, молниеносно перерендериться
весь наш компонент и обновит все значения свои, где он на этот стейт и ссылался.
То есть, как только в коде мы поменяем значение `title`, молниеносно на экране браузера
мы получим его новое значение. Ну не круто ли? Сейчас просто комплесно сравним 
старый императивный подход к разработке и новый декларативный подход. Всё познается
в сравнении. 

# Сравнение

```html 
<template id="app">
    <div class="num">{{ number }}</div>
</template>

<script>
    $('#app')
      .state({ number: 0 })
      .on('click', '.num', state => {
        state.number = state.number + 1;
      })
      .mount()
</script>
```
Этот код вывод на страницу символ 0, и каждый раз когда ты будешь на него кликать, 
он будет увеличиваться ровно на еденицу. Теперь посмотрим тот же код на jQuery.
```html 
<div class="num">0</div>

<script>
    let num = 0;
    
    $('.num').on('click', function() {
        num++;
        $('.num').innerText = num;
    });
</script>
```
Чувствуете разницу, как код становится комплекснее и грязнее? Когда мы целиком берём 
ответственность за переменную? Сейчас это называется императивный подход - это подход,
когда мы контролируем каждый чих, вместо доверия. Декларативность же, напротив, делает 
всё сама, главное скажи что делать. 

А теперь представьте что стейт широкий у приложения? Что в нём не один маленький `let num = 0`, 
а реально тонна, как и полагается более-менее сложному приложению? Представили? Ну как? 
Нравится картина? Это старая боль JS разработчиков. Ровно за этим фреймворки и придумывались.
Поддерживаемость такого подхода нулевая или околонулевая, в сравнении с декларативностью.

В реактивных движках мы следим лишь за стейтом. Мы выносим за скобки весь перерендер, 
и оставляем его на волю движка доверяя ему как чёрному ящику, что он сделает всё в лучшем 
виде. А это мы ещё не переходили к созданию динамического HTML'a - очень частая задача 
в среде браузерного JS. Когда наш шаблонизатор умеет итерировать и создавать динамику 
прямо в HTML'e `w-for`, то мы попадаем буквально в сказку! 

# Сравнение 2 

Wex-реактивная библиотека. Декларативный подход.
```html 
<template id="app">
    <div class="list" w-for="listItem in list">
        <ul>
            <li>{{ listItem }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({ list: ['privet', 'kak', 'dela'] })
      .mount()
</script>
```
jQuery-нереактивная библиотека. Императивный подход.
```html 
<div class="list">
    <ul></ul>
</div>

<script>
    const list = ['privet', 'kak', 'dela'];

    list.forEach(item => {
        $('ul').append('<li>' + item + '</li>');
    });
</script>
```

О, нет! HTML прямо в JS... Уже пахнет вонючим кодом... Но да, так и есть. Действительно: 
это полное нарушение MVC-паттерна, вывод смешался с логикой. Так не должно быть. 
Мы по факту организовали шаблонизатор в коде и это плохо. Но отставим красоту и паттерны.
Взгляните чистым свежим взглядом: какой подход Вам более понятен, близок и по душе?

Если второй, ничего страшного. Раздутый JS с кусками HTML внутри это не страшно,
можно поддерживать. Да, тяжело. Но можно. Если же Вам понравился первый вариант,
то значит реактивность это то, что Вам нужно!

## Сравнение 3. TODO-Приложение.

TODO-Приложения, казалось бы, достаточно легки в реализации, но это отнюдь не так.
Это всегда комплексные и масштабные приложения с витиеватой логикой. 
Но давайте попробуем такое комплексное приложение реализовать на Wex!

```html 
<div>
    <template id="app">
        <div>
            <input w-bind="newTodo" placeholder="Новая задача..." />
            <button w-on="click:addTodo">Добавить</button>

            <div w-for="todo,index in todos traceby todo.id">
                <span>{{ todo.text }}</span>
                <button w-on="click:remove(todo.id)">Удалить</button>
            </div>
        </div>
    </template>
</div>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>

<script>
    $('#app')
        .state(() => ({
            newTodo: '',
            todos: [],
        }))

        // Кнопка добавить
        .method('addTodo', function (state) {
            // Наш инупт забинжен через w-bind="newTodo", данные сразу тут будут
            let inputText = state.newTodo.trim()

            let newTodo = {
                id: Date.now(), // даём уникальный ид
                text: inputText // заносим сюда текст из инпута
            }

            state.todos.push(newTodo) // пушим наш новый туду в стейт
            state.newTodo = '' // очищаем инпут, ведь он забинжен и очистится вместе со стейтом
        })

        // Кнопка удалить
        .method('remove', function (state, id) {
            
            // формируем список новых тудушек, покаместь пустой
            let newTodos = []

            // пробегаемся по текущим тудушкам чтобы вычислить все айдишники
            for (let i = 0; i < state.todos.length; i++) {

                // создаём новую локальную переменную с текущей тудушкой
                let todo = state.todos[i]

                // проверяем что текущая тудушка из нашей for-крутилки 
                // не равна айдишнику удаляемой тудушки
                if (todo.id !== id) {

                    // все остальные тудушки кроме текущей удаляемой добавляем в новый список
                    newTodos.push(todo)
                }
            }

            // реактивно обновляем стейт новыми тудушками без той что мы удалили
            state.todos = newTodos
        })

        .mount()
</script>
```

# Двойное связывание (он же биндинг)

Чтобы нам не приходилось вручную писать алгоритм связи вводимых пользователем данных
и нашего стейта, было придумано понятие биндинга. Двусторонний биндинг, это по сути
зависимость стейта от вводимых данных. То, что написано в инпуте, моментально 
летит в стейт, и то, что изменилось в стейте, моментально меняется в инпуте. 
По сути так и строится вся реактивность. Рассмотрим на примере. 

```html 
<template id="app">
    <input w-bind="mytext">
    <span>Вы ввели: {{ mytext }}</span>
</template>

<script>
    $('#app')
      .state({ mytext: '' })
      .mount()
</script>
```

Таким простым способом мы сделали реактивный вывод вводимых данных.

## Поддерживаемые элементы для биндинга

`w-bind` работает на трёх типах элементов — `input`, `textarea` и `select`. 
Принцип одинаков для всех: пользователь что-то выбирает или вводит — стейт обновляется мгновенно.

```html 
<template id="app">
    <input w-bind="name" placeholder="Имя">
    <textarea w-bind="comment" placeholder="Комментарий"></textarea>
    <select w-bind="city">
        <option value="kh">Харьков-Царь</option>
        <option value="odessa">Одесса-мама</option>
        <option value="kiev">Киев-Русь</option>
    </select>

    <p>Имя: {{ name }}</p>
    <p>Комментарий: {{ comment }}</p>
    <p>Город: {{ city }}</p>
</template>

<script>
    $('#app')
      .state({ name: '', comment: '', city: 'kh' })
      .mount()
</script>
```
⚠ `w-bind` — это именно двусторонняя связь. Если вы поменяете значение в стейте программно, 
инпут тоже обновится. Это отличает его от `w-value`, который работает только в одну сторону 
— из стейта в элемент.

## Предзаполненный стейт
Начальное значение в стейте автоматически попадёт в поле при монтировании. 
Удобно для форм редактирования:
```html 
<template id="app">
    <input w-bind="username">
    <span>Привет, {{ username }}!</span>
</template>

<script>
    $('#app')
      .state({ username: 'Рустам' })
      .mount()
</script>
```
Пользователь сразу увидит своё имя в поле и сможет его отредактировать — стейт 
подхватит изменения на лету. 

# Условный вывод

Иногда бывают ситуации необходимости вывести-скрыть определенный блок со страницы.
Имея под собой реактивность и стейт, а так же мощный шаблонизатор, это становится
рядовой и тривиальной задачей. Усложним предыдущий пример.

```html 
<template id="app">
    <input w-bind="mytext">
    <span>Вы ввели: {{ mytext }}</span>
    <div w-if="mytext === 'фильм'">
        Вы ввели слово фильм! Тайный блок открыт!
    </div>
</template>

<script>
    $('#app')
      .state({ mytext: '' })
      .mount()
</script>
```

## Как работает w-if

`w-if` принимает любое JavaScript-выражение, которое приводится к `true` или `false`. 
Если выражение истинно — элемент рендерится в DOM, если нет — его там просто нет.
Это важное отличие от простого CSS-скрытия: элемент не просто становится невидимым, 
он физически отсутствует в дереве до тех пор, пока условие не выполнится.

```html 
<template id="app">
    <input w-bind="age" placeholder="Введите возраст">

    <div w-if="age >= 18">
        Добро пожаловать!
    </div>
    <div w-if="age > 0 && age < 18">
        Доступ только с 18 лет.
    </div>
</template>

<script>
    $('#app')
      .state({ age: '' })
      .mount()
</script>
```

## Переключение по булевому флагу
Самый частый сценарий — показать или скрыть блок по кнопке. 
Для этого в стейте держим флаг и меняем его через `on`:
```html 
<template id="app">
    <button class="toggle-btn">Показать детали</button>

    <div w-if="!!isOpen">
        Здесь скрытые детали, которые видны только после нажатия.
    </div>
</template>

<script>
    $('#app')
      .state({ isOpen: false })
      .on('click', '.toggle-btn', state => {
          state.isOpen = !state.isOpen;
      })
      .mount()
</script>
```
`!!isOpen` — двойное отрицание явно приводит значение к булевому типу. 
Хорошая привычка, особенно когда в стейте могут оказаться `null` или `undefined`.

## w-if внутри w-for

`w-if` и `w-for` отлично уживаются вместе — можно фильтровать элементы списка прямо в шаблоне:
```html 
<template id="app">
    <div w-for="item,index in products traceby item.id">
        <div w-if="!!item.inStock">
            {{ index + 1 }}. {{ item.name }} — в наличии
        </div>
    </div>
</template>

<script>
    $('#app')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   inStock: true  },
              { id: 2, name: 'Молоко', inStock: false },
              { id: 3, name: 'Сыр',    inStock: true  },
          ]
      })
      .mount()
</script>
```
Молоко не попадёт в DOM вовсе — только товары с `inStock: true`.

# Цикличный вывод

Порой нам надо динамически просмотреть стейт и вывести всё его состояние. Для этого 
в шаблоне реализована директива `w-for`, которая базово выглядит следующим образом:

```html 
<template id="app">
    <div class="list" w-for="listItem in list">
        <ul>
            <li>{{ listItem }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({ list: ['privet', 'kak', 'dela'] })
      .mount()
</script>
```

Здесь происходит перебор значений из массива стейта и вывод их по заданному шаблону.

## Индекс элемента

Если помимо значения нужен порядковый номер элемента, достаточно добавить второй аргумент 
— без пробела между ними:

```html 
<template id="app">
    <div class="list" w-for="listItem,index in list">
        <ul>
            <li>{{ index + 1 }}. {{ listItem }}</li>
        </ul>
    </div>
</template>
```
⚠ Важно: `listItem,index` — без пробела внутри. `,index` необязателен.

## Traceby — отслеживание уникальных элементов

Когда список меняется (элементы добавляются, удаляются, перемещаются), 
WEX по умолчанию перерисовывает весь блок целиком. Это работает, но неэффективно — 
особенно если список большой или элементы содержат сложную вёрстку.

Traceby говорит фреймворку: «смотри не на позицию элемента, а на конкретное поле — 
и перерисовывай только то, что реально изменилось».

```html 
<template id="app">
    <div class="list" w-for="item,index in users traceby item.id">
        <ul>
            <li>{{ index + 1 }}. {{ item.name }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({
          users: [
              { id: 1, name: 'Алиса' },
              { id: 2, name: 'Боб' },
              { id: 3, name: 'Вера' },
          ]
      })
      .mount()
</script>
```
Теперь если в массив добавится новый пользователь или один из них удалится — 
WEX не будет трогать узлы с уже знакомыми id. Это экономит ресурсы и исключает 
визуальные мигания при обновлении.

## Вывод обьектов
На практике `w-for` чаще всего работает не с плоскими строками, а с массивом объектов. 
Обращаться к полям можно напрямую через точку:
```html 
<template id="app">
    <div class="list" w-for="product,index in products traceby product.id">
        <ul>
            <li>{{ index + 1 }}. {{ product.name }} — {{ product.price }} ₽</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   price: 45  },
              { id: 2, name: 'Молоко', price: 89  },
              { id: 3, name: 'Сыр',    price: 320 },
          ]
      })
      .mount()
</script>
```

# Атрибуты-директивы

Помимо биндинга и условного вывода, WEX предоставляет набор специальных атрибутов, 
которые управляют поведением и внешним видом элементов прямо из стейта. 
Все они работают по одному принципу: значение в стейте меняется — атрибут на элементе 
меняется автоматически. Не нужно руками лезть в DOM, писать `$('.btn').addClass(...) `
или `$('img').attr('src', ...)` — шаблон САМ за всем следит.

## w-value — значение поля из стейта

Устанавливает значение `input`, `textarea` или `select` односторонне — только из стейта в элемент. 
В отличие от `w-bind`, изменения пользователя обратно в стейт не летят.
Используется когда нужно просто отобразить данные в поле, не слушая ввод:
```html 
<template id="app">
    <input w-value="username" placeholder="Имя пользователя">
    <textarea w-value="bio"></textarea>
    <select w-value="role">
        <option value="admin">Администратор</option>
        <option value="user">Пользователь</option>
    </select>
</template>

<script>
    $('#app')
      .state({
          username: 'Алиса',
          bio: 'Люблю котиков и кофе.',
          role: 'admin'
      })
      .mount()
</script>
```

`w-value` — читает стейт и всё, ничего более. `w-bind` — читает и перезаписывает его обратно. 
Другими словами `w-value` иммутабельный ридер, в том время как `w-bind` мутабельный ридер-райтер.
Если нужна форма редактирования, берите `w-bind`. Если просто показать данные в поле — `w-value`.

## w-class — динамические классы

Позволяет добавлять и убирать CSS-классы в зависимости от условий стейта. 
По сути тот же `w-if`, только работает с классами. 
Принимает объект, где ключ — имя класса, значение — условие:
```html 
<template id="app">
    <button class="toggle-btn">Переключить</button>

    <div w-class="{ 'active': !!isActive, 'highlighted': score > 50 }">
        Этот блок меняет классы
    </div>

    <p>Очки: {{ score }}</p>
</template>

<script>
    $('#app')
      .state({ isActive: false, score: 75 })
      .on('click', '.toggle-btn', state => {
          state.isActive = !state.isActive;
      })
      .mount()
</script>
```

Класс active появится когда `isActive` станет `true`. Класс `highlighted` уже висит 
с самого начала — потому что score равен 75. Обычный атрибут `class` и `w-class`
прекрасно уживаются на одном элементе.

## w-disabled — блокировка элементов

Делает элемент недоступным для взаимодействия. Работает на `input`, `textarea`, `select` и `button`:
```html 
<template id="app">
    <input w-bind="email" placeholder="Email">
    <button class="submit-btn" w-disabled="!isValid">Отправить</button>
</template>

<script>
    $('#app')
      .state({ email: '', isValid: false })
      .on('input', 'input', state => {
          state.isValid = state.email.includes('@');
      })
      .mount()
</script>
```

Кнопка заблокирована до тех пор, пока пользователь не введёт корректный email. 
Никакого ручного `$('button').prop('disabled', true)` — стейт сам всем управляет.

## w-checked — чекбоксы и радиокнопки

Управляет состоянием checked у `input[type=checkbox]` и `input[type=radio]`:
```html 
<template id="app">
    <label>
        <input type="checkbox" w-checked="!!agree">
        Я согласен с условиями
    </label>

    <input type="radio" name="size" value="s" w-checked="size === 's'"> S
    <input type="radio" name="size" value="m" w-checked="size === 'm'"> M
    <input type="radio" name="size" value="l" w-checked="size === 'l'"> L

    <p w-if="!!agree">Размер выбран: {{ size }}</p>
</template>

<script>
    $('#app')
      .state({ agree: false, size: 'm' })
      .mount()
</script>
```

Для чекбокса — просто булевое значение. Для радиокнопок — сравнение 
текущего значения стейта с `value` конкретной кнопки. При монтировании `M` будет 
отмечен автоматически, потому что `size: 'm'`.

## w-selected — выбранный option

Управляет атрибутом `selected` у отдельных option внутри `select`. 
Удобно когда список опций генерируется через `w-for`:
```html 
<template id="app">
    <select>
        <option
            w-for="city in cities traceby city.id"
            w-selected="chosenId === city.id"
            w-value="city.id">
            {{ city.name }}
        </option>
    </select>

    <p>Выбран город с id: {{ chosenId }}</p>
</template>

<script>
    $('#app')
      .state({
          chosenId: 2,
          cities: [
              { id: 1, name: 'Париж' },
              { id: 2, name: 'Харьков' },
              { id: 3, name: 'Техас' },
          ]
      })
      .mount()
</script>
```

Харьков будет выбран по умолчанию — потому что `chosenId: 2` совпадает с его `id`.

## w-src — источник изображения

Устанавливает атрибут `src` у картинки из стейта. Всегда используйте `w-src` вместо 
обычного `src` когда путь к изображению динамический — иначе браузер попытается 
загрузить `src="{{avatarUrl}}"` буквально:

```html 
<template id="app">
    <div w-for="user in users traceby user.id">
        <img w-src="user.avatar" alt="Аватар">
        <span>{{ user.name }}</span>
    </div>
</template>

<script>
    $('#app')
      .state({
          users: [
              { id: 1, name: 'Алиса', avatar: '/images/alice.jpg' },
              { id: 2, name: 'Боб',   avatar: '/images/bob.jpg'   },
          ]
      })
      .mount()
</script>
```

## w-id — уникальный идентификатор узла

Присваивает виртуальному узлу стабильный внутренний идентификатор. 
WEX использует его при диффинге — чтобы точно понять какой DOM-элемент обновить, 
а какой не трогать:

```html 
<template id="app">
    <div w-for="msg in messages traceby msg.id">
        <div w-id="msg-{{msg.id}}" w-class="{ 'unread': !msg.read }">
            {{ msg.text }}
        </div>
    </div>
</template>

<script>
    $('#app')
      .state({
          messages: [
              { id: 1, text: 'Привет!',    read: true  },
              { id: 2, text: 'Как дела?',  read: false },
              { id: 3, text: 'Ответишь?',  read: false },
          ]
      })
      .mount()
</script>
```
`w-id` особенно полезен когда несколько однотипных блоков существуют рядом 
и нужно исключить путаницу при перерисовке. Значение должно быть стабильным 
и уникальным в пределах одного шаблона.

# Обработка событий через шаблон

До этого момента мы вешали все обработчики событий в скрипте через `.on()`. 
Это основной и рекомендуемый способ в WEX. Но иногда удобнее объявить связь 
прямо в шаблоне — особенно когда элементов много и каждый должен вызывать 
свою функцию. Для этого существует директива `w-on`.

Главное что нужно понять: `w-on` не живёт без `fn`. Директива в шаблоне — это 
только половина, она лишь указывает имя функции. Саму функцию нужно 
зарегистрировать в скрипте через `.fn()`.

```html 
<template id="app">
    <input w-bind="message" placeholder="Введите сообщение">
    <button w-on="click:handleSubmit">Отправить</button>
    <p w-if="!!sent">Сообщение отправлено: {{ message }}</p>
</template>

<script>
    $('#app')
      .state({ message: '', sent: false })
      .method('handleSubmit', state => function(e) {
          state.sent = true;
      })
      .mount()
</script>
```

Синтаксис `w-on="событие:имяФункции"` — событие это любое DOM-событие: 
`click`, `input`, `change`, `submit`, `keyup` и так далее.

## Несколько событий на разных элементах

Когда в шаблоне много интерактивных элементов, `w-on` позволяет держать связи 
прямо в разметке — не нужно угадывать по селектору в скрипте что к чему относится:

```html 
<template id="app">
    <input w-bind="query" w-on="input:onSearch" placeholder="Поиск...">
    <button w-on="click:onClear">Очистить</button>
    <button w-on="click:onSubmit">Найти</button>

    <p>Результат: {{ result }}</p>
</template>

<script>
    $('#app')
      .state({ query: '', result: '' })
      .method('onSearch', state => function(e) {
          state.result = state.query.length > 0
              ? `Ищем: "${state.query}"`
              : '';
      })
      .method('onClear', state => function(e) {
          state.query  = '';
          state.result = '';
      })
      .method('onSubmit', state => function(e) {
          state.result = `Запрос отправлен: "${state.query}"`;
      })
      .mount()
</script>
```

## w-on внутри w-for

Особенно `w-on` раскрывается в списках — когда каждый элемент должен реагировать 
на событие со своими данными. Через `.fn()` в `state` уже доступен весь контекст:

```html 
<template id="app">
    <div w-for="item,index in cart traceby item.id">
        <span>{{ item.name }} — {{ item.qty }} шт.</span>
        <button w-on="click:onRemove">Удалить</button>
    </div>
    <p>Итого позиций: {{ cart.length }}</p>
</template>

<script>
    $('#app')
      .state({
          cart: [
              { id: 1, name: 'Хлеб',   qty: 2 },
              { id: 2, name: 'Молоко', qty: 1 },
              { id: 3, name: 'Сыр',    qty: 3 },
          ]
      })
      .method('onRemove', state => function(e) {
          const btn   = $(this);
          const index = btn.closest('[w-for]').index();
          state.cart.splice(index, 1);
          this.update();
      })
      .mount()
</script>
```

Когда вы меняете массив методами вроде `splice`, `push` или `sort` — 
WEX не всегда замечает изменение автоматически. В таких случаях 
вызывайте `this.update()` вручную внутри функции — `this` внутри обработчика это сам `view`.

## Разница между w-on и .on()

| Описание различия | `w-on` в шаблоне     | `.on()` в скрипте        |
|------------------|--------------------|--------------------------|
| Где описана связь | прямо на элементе   | в скрипте по селектору   |
| Нужен ли `fn`    | обязательно         | нет, логика inline       |
| Удобно когда     | много разных кнопок | одно событие на группу    |
| Читаемость       | видно в шаблоне     | видно в скрипте          |

Оба подхода рабочие. Можно смешивать в одном приложении — никаких конфликтов нет.

# Статические узлы

Реактивность — это удобно, но не бесплатно. При каждом изменении стейта 
WEX проходит по шаблону, сравнивает виртуальное дерево с реальным DOM 
и обновляет то, что изменилось. Для большинства элементов это быстро, 
но если в шаблоне есть блоки которые никогда не зависят от стейта — 
зачем тратить на них время при каждом перерендере?

Именно для этого существует `w-static`. Один раз отрисовал — и больше не трогаю.

```html 
<template id="app">
    <div w-static>
        <h1>Добро пожаловать в наш магазин</h1>
        <p>Работаем с 2010 года. Доставка по всей стране.</p>
    </div>

    <p>Товаров в корзине: {{ cartCount }}</p>
    <button class="add-btn">Добавить</button>
</template>

<script>
    $('#app')
      .state({ cartCount: 0 })
      .on('click', '.add-btn', state => {
          state.cartCount++;
      })
      .mount()
</script>
```

Заголовок и описание отрисуются один раз при монтировании. 
Сколько бы раз `cartCount` ни менялся — WEX не будет заходить в этот блок вообще.

## Когда w-static особенно полезен

Статичные шапки, футеры, иконки, рекламные баннеры, длинные текстовые блоки — 
всё что не меняется в зависимости от данных. Особенно заметный эффект даёт 
разметка со сложной структурой или большим количеством вложенных тегов:

```html 
<template id="app">
    <header w-static>
        <nav>
            <a href="/">Главная</a>
            <a href="/catalog">Каталог</a>
            <a href="/about">О нас</a>
            <a href="/contacts">Контакты</a>
        </nav>
    </header>

    <main>
        <p>Привет, {{ username }}!</p>
        <button class="logout-btn">Выйти</button>
    </main>

    <footer w-static>
        <p>© 2024 Все права защищены</p>
    </footer>
</template>

<script>
    $('#app')
      .state({ username: 'Алиса' })
      .on('click', '.logout-btn', state => {
          state.username = 'Гость';
      })
      .mount()
</script>
```

header и footer заморожены навсегда. При клике на кнопку обновится только 
`username` внутри main — WEX даже не посмотрит в сторону статичных блоков.

⚠ `w-static` — необратимо. После первого рендера блок отвязывается 
от реактивной системы полностью. Не используйте его там где 
данные могут измениться — даже если сейчас кажется что не изменятся.

# Как WEX работает под капотом

Когда вы пишете `.state({...}).mount()` — снаружи всё выглядит как магия. 
Данные меняются, страница обновляется сама. Но внутри происходит чёткая 
последовательность шагов, понимание которой помогает писать более осознанный 
код и объясняет почему одни вещи работают именно так, а не иначе.

## Реактивный стейт — прокси над объектом

Первое что делает WEX при монтировании — оборачивает ваш объект состояния в `Proxy`. 
Это стандартный JavaScript-механизм перехвата операций над объектом.
```html 
$('#app')
  .state({ count: 0 }) // ← этот объект станет Proxy
  .mount()
```

Каждый раз когда вы делаете `state.count = 5` внутри обработчика — `Proxy` перехватывает 
это присвоение и вызывает `nextTick`. Сам `nextTick` — это `throttle-функция` с задержкой 
16 миллисекунд (одного кадра). Это значит что если вы изменили стейт десять раз подряд 
в одном обработчике — перерисовка произойдёт один раз, по истечении 16мс. 
Никаких лишних перерисовок.

```js 
.on('click', '.btn', state => {
    state.a = 1  // ← Proxy поймал
    state.b = 2  // ← Proxy поймал
    state.c = 3  // ← Proxy поймал
    // перерисовка будет одна, через ~16мс
})
```

## Цикл рендеринга в 4 шага.

Каждый раз когда стейт изменился и пришло время обновить DOM, WEX запускает функцию `render`. 
Внутри неё происходят четыре фазы строго по порядку: `prepare` → `compile` → `diffAndPatch` → `affect`

### 1. prepare — сброс эффектов

Перед новым рендером WEX обходит все ранее зарегистрированные записи скомпилированных узлов 
и вызывает у каждого функцию `revoke` — если она есть. Это чистка побочных эффектов прошлого 
рендера: снятие обработчиков событий, отписки от наблюдателей.

Именно поэтому `w-bind` не накапливает бесконечные `input`-листенеры при каждом ре-рендере 
— каждый прошлый листенер аккуратно снимается перед новым рендером.

### 2. compile — виртуальное дерево

WEX берёт HTML-строку из вашего `<template>` и строит из неё новое дерево узлов — 
но не в реальный DOM, а в отдельный `<div>` в памяти. На этом этапе:
- обрабатываются все директивы (`w-for`, `w-if`, `w-class` и остальные)
- интерполируются все `{{ выражения }}`
- создаются или переиспользуются экземпляры дочерних компонентов

Результат — массив готовых DOM-узлов, которые пока ни к чему не подключены.

### 3. diffAndPatch — умное обновление

Вот здесь и живёт главная оптимизация. WEX не заменяет весь DOM — 
он сравнивает только что скомпилированное дерево с тем что уже стоит 
на странице, и точечно обновляет только то что изменилось.

| Было в DOM       | Пришло новое      | Итог                  |
|------------------|-----------------|----------------------|
| `<li>Хлеб</li>`   | `<li>Хлеб</li>`  | не тронуто           |
| `<li>Молоко</li>` | `<li>Кефир</li>` | textContent обновлён  |
| `<li>Сыр</li>`    | (нет)            | удалён               |

При сравнении узлов WEX смотрит на `id`, `data-id` и `w-id` — именно поэтому 
`traceby` в `w-for` так важен. Без него фреймворк ориентируется только 
по позиции и типу тега, что менее точно.

### 4. affect — живые эффекты
После того как DOM обновлён, WEX проходит по всем скомпилированным 
записям ещё раз и запускает функции `affect` — это финальная фаза 
где директивы получают доступ к реальным DOM-элементам. 
Именно здесь `w-bind` вешает input-листенер, `w-src` ставит настоящий 
`src` на картинку, `w-on` регистрирует обработчик событий через `view.on`.

Разделение `compile` и `affect` сделано намеренно: на этапе компиляции 
элементы ещё не в DOM, события на них вешать бессмысленно.

## Как w-static выключается из этого цикла

Теперь понятно почему w-static такой эффективный. Заглянув в исходник 
можно увидеть что это вовсе не специальная директива — это компонент, 
который подписывается на внутреннее событие $update и немедленно вызывает prevent():
```js 
component(
  'w-static',
  () => $('<template><slot></slot></template>')
    .state()
    .on('$update', () => (e, state, prevent) => {
      prevent()  // ← просто говорит "не надо меня перерисовывать"
    })
)
```

Первый рендер проходит нормально. При каждом последующем вызове `render` 
— компонент блокирует фазу `compile` для своего поддерева. 
До `diffAndPatch` дело просто не доходит.

## Вся картина целиком
```
   Изменился стейт
      ↓
   Proxy перехватил
      ↓
   nextTick (ждём 16мс, собираем все изменения)
      ↓
   render()
      ↓
   prepare()        — снимаем старые эффекты
      ↓
   compile()        — строим новое дерево в памяти
      ↓             ↑
      |             w-static → prevent() → стоп, этот узел пропускаем
      ↓
   diffAndPatch()   — сравниваем с реальным DOM, патчим точечно
      ↓
   affect()         — вешаем живые эффекты на реальные элементы
      ↓
   DOM обновлён.
```

Именно эта архитектура делает WEX предсказуемым: стейт — 
единственный источник правды, DOM — лишь его отражение. 
Вы никогда не трогаете DOM напрямую, а фреймворк сам разбирается 
что изменить, что оставить и что пропустить совсем.

# Хранилище (Store)

Представьте что пользователь набрал очки в игре, заполнил форму 
или выбрал тему оформления — и вдруг обновил страницу. 
Всё сбросилось. Стейт WEX живёт только в памяти браузера, 
и при перезагрузке возвращается к начальным значениям.
Чтобы этого не происходило, в WEX есть встроенный механизм сохранения — Store. 

Достаточно положить нужные данные в специальный ключ стейта с именем storage, 
и фреймворк автоматически будет синхронизировать их с localStorage браузера. 
Данные переживут перезагрузку, закрытие вкладки и возврат на страницу.

```html 
<template id="score">
    <p>Score: {{ storage.score }}</p>
    <button class="increase-btn">Increase</button>
</template>

<script>
    $('#score')
        .state({
            storage: {
                score: 0,
                test: 1,
            }
        })
        .on('click', '.increase-btn', state => {
            state.storage.score = ++state.storage.score;
        })
        .mount()
</script>
```

Всё что находится внутри `storage` — сохраняется. Всё что снаружи — 
живёт только до перезагрузки. Это намеренное разделение: 
вы сами решаете что важно сохранить, а что нет.

## Что происходит под капотом

WEX следит за `storage` в двух точках жизненного цикла:

При монтировании (`$mount`) — фреймворк смотрит есть ли в `localStorage` 
сохранённые значения для каждого ключа из `storage`. Если есть — загружает 
их в стейт, и пользователь видит свои прошлые данные. Если нет — записывает 
текущие начальные значения как точку отсчёта.

При каждом изменении стейта (`$change`) — если данные в `storage` изменились, 
они немедленно записываются в `localStorage`. Синхронизация происходит автоматически, 
вам не нужно ничего вызывать вручную.

```
Первый визит:          Повторный визит:
-------------------------------------------------
storage.score = 0      localStorage → score = "7"
```

## Что хранить в storage
Store хорошо подходит для данных которые должны пережить перезагрузку:
- счётчики и прогресс
- выбранный язык или тема оформления
- содержимое корзины
- состояние формы которую пользователь не дозаполнил
- любые пользовательские настройки

```js 
$('#app')
    .state({
        theme: 'light',       // ← не сохранится
        username: '',         // ← не сохранится
        storage: {
            lang: 'ru',       // ← сохранится
            fontSize: 16,     // ← сохранится
            darkMode: false,  // ← сохранится
        }
    })
    .mount()
```

## Важно знать!
⚠ localStorage хранит только строки. WEX автоматически сериализует 
значения через JSON.stringify при записи и JSON.parse при чтении. 
Это означает что числа, булевы значения и вложенные объекты работают 
корректно — но при чтении из пустого хранилища всегда проверяйте 
что значение не null.

⚠ localStorage ограничен объёмом около 5 МБ на домен. 
Для хранения больших массивов данных или файлов он 
не подходит — держите в storage только лёгкие настройки и счётчики.

⚠ Данные в localStorage привязаны к домену и браузеру. 
Если пользователь откроет сайт в другом браузере или 
режиме инкогнито — история не перенесётся.

# Хуки жизненного цикла
Любой компонент в WEX проходит через определённые этапы — появляется на странице, 
обновляется когда меняются данные, и в какой-то момент исчезает. 

Хуки — это способ встроиться в эти этапы и выполнить свой код в нужный момент.

Технически это обычный `.on()`, но вместо DOM-событий вроде `click` или 
`input` — специальные внутренние события, которые начинаются с `$`. 
WEX сам вызывает их в нужное время, вам остаётся только подписаться.

## $mount — компонент появился на странице

Срабатывает один раз, сразу после того как вью вставлена в DOM. 
Идеальное место для загрузки начальных данных, запросов к API или любой инициализации:

```html 
<template id="app">
    <div w-if="!!loading">Загрузка...</div>
    <div w-if="!loading">
        <p>Привет, {{ username }}!</p>
    </div>
</template>

<script>
    $('#app')
      .state({ username: '', loading: true })
      .on('$mount', state => {
          setTimeout(() => {
              state.username = 'Алиса';
              state.loading = false;
          }, 1500)
      })
      .mount()
</script>
```

Пользователь видит «Загрузка...» пока данные не пришли — затем 
WEX автоматически перерисовывает шаблон.

## $unmount — компонент убран со страницы

Срабатывает когда вы вызываете `view.unmount()`. Место для чистки — остановить таймеры, 
отписаться от внешних событий, сбросить что-то в исходное состояние:
```html 
<template id="timer">
    <p>Прошло секунд: {{ seconds }}</p>
    <button class="stop-btn">Остановить</button>
</template>

<script>
    let interval = null;

    const view = $('#timer')
      .state({ seconds: 0 })
      .on('$mount', state => {
          interval = setInterval(() => {
              state.seconds++;
          }, 1000);
      })
      .on('$unmount', state => {
          clearInterval(interval);
      })
      .on('click', '.stop-btn', state => {
          view.unmount();
      })
      .mount()
</script>
```
Без `$unmount` таймер продолжал бы тикать в фоне даже после исчезновения компонента.

## $change — стейт изменился

Срабатывает каждый раз когда любое значение в стейте меняется. 
Удобно для слежения за данными, логирования или синхронизации с внешними системами:
```html 
<template id="form">
    <input w-bind="query" placeholder="Введите запрос">
    <p>Символов: {{ length }}</p>
</template>

<script>
    $('#form')
      .state({ query: '', length: 0 })
      .on('$change', state => {
          state.length = state.query.length;
      })
      .mount()
</script>
```

⚠ Будьте осторожны — если внутри `$change` снова менять стейт, это вызовет ещё один `$change`. 
Следите чтобы не получилась бесконечная цепочка.

## $render — шаблон перерисован

Срабатывает после каждой перерисовки DOM. Нужен когда важно работать с реальными 
элементами уже после того как они появились или обновились — например 
инициализировать стороннюю библиотеку:

```html 
<template id="chart">
    <canvas class="my-canvas"></canvas>
</template>

<script>
    $('#chart')
      .state({ data: [10, 20, 30] })
      .on('$render', state => {
          // canvas уже в DOM, можно рисовать
          const canvas = document.querySelector('.my-canvas');
          // ... инициализация графика
      })
      .mount()
</script>
```

## $destroy — компонент уничтожен

Срабатывает при вызове view.destroy() — это жёстче чем unmount. 
Компонент не просто скрывается, а полностью удаляется вместе 
со всеми подписками. Используется для финальной очистки:

```js 
const view = $('#app')
  .state({ ... })
  .on('$destroy', state => {
      console.log('Компонент уничтожен, прощай')
      // финальная очистка, освобождение ресурсов
  })
  .mount()

// Где-то позже:
view.destroy()
```

## Вся цепочка жизни компонента
```
   .mount() вызван
      ↓
   $mount — компонент в DOM, можно инициализировать
      ↓
   стейт изменился
      ↓
   $change — данные обновились
      ↓
   $render — DOM перерисован
      ↓
   .unmount() вызван
      ↓
   $unmount — компонент ушёл, чистим за собой
      ↓
   .destroy() вызван
      ↓
   $destroy — всё, компонент больше не существует
```

## Сравнение хуков

| Хук        | Когда срабатывает                     | Типичное применение                                      |
|------------|--------------------------------------|----------------------------------------------------------|
| `$mount`   | Один раз, при появлении в DOM         | Загрузка данных, запросы                                 |
| `$change`  | При каждом изменении стейта           | Слежение, синхронизация                                  |
| `$render`  | После каждой перерисовки              | Работа со сторонними библиотеками                        |
| `$unmount` | При скрытии компонента                | Очистка таймеров, отписки                                |
| `$destroy` | При полном уничтожении                | Финальная очистка ресурсов                                |
| `$route`   | При смене роута                       | Когда нужен полный контроль роутинговой системы SPA      |
| `$wiring`  | При загрузке данных через `$wire()`   | Когда нужен полный контроль загрузки и обработки ошибок |

# Компоненты

Если вы пришли из мира jQuery, скорее всего ваш код выглядит примерно так:
большой HTML-файл, много $('.что-то').on(...), и всё в одном месте.
Это работает — но когда проект растёт, один и тот же кусок разметки
начинает копироваться по странице, а правка в одном месте требует правки
во всех остальных.

Компонент — это переиспользуемый кусок шаблона со своим стейтом.
Один раз описали карточку товара, кнопку или иконку — и вставляете их в
любое место как обычный HTML-тег. WEX сам разберётся как это отрисовать.

Дальше мы пройдём весь путь по порядку: сначала компоненты внутри единой страницы,
потом вынесем их в отдельные файлы, научим общаться между собой,
дадим им общий стейт и в конце разберёмся, как не грузить лишнее.

# Компоненты внутри единой страницы

## Первый компонент — иконка

Представьте что по всему сайту используются иконки, и каждый раз писать
`<i class="icon icon-search"></i>` надоело. Вынесем это в компонент:

```js
const { component } = window.jqvm

const icon = $(`<i class="icon icon-{{type}}"></i>`)
  .state(() => ({ type: 'eye' })) // начальное значение по умолчанию

component('icon', icon)
```

Теперь в любом шаблоне можно писать просто:
```html
<template id="app">
    <icon type="search"></icon>
    <icon type="heart"></icon>
    <icon type="user"></icon>
</template>
```

WEX подставит нужный тип и каждый раз отрисует правильную иконку.
Захотели изменить структуру иконки — меняете в одном месте, обновится везде.

```
Заметьте: в .state() передаётся функция, которая возвращает объект —
а не сам объект напрямую. Это важно: каждый экземпляр компонента
получает свою независимую копию стейта. Если передать объект напрямую —
все иконки на странице будут делить один стейт и менять друг друга.
```

## Пропсы — передача данных внутрь

Пропсы это то что вы передаёте компоненту снаружи — как атрибуты HTML-тега.
Есть три способа:

Обычная строка — просто пишете значение:
```html
<icon type="search"></icon>
```
Выражение из стейта — ставите : перед именем,
и WEX вычислит значение из текущего стейта родителя:
```html
<icon :type="currentIcon"></icon>
<!-- currentIcon берётся из state родительского шаблона -->
```
Функция-обработчик — ставите @, чтобы компонент мог сообщить родителю о событии:
```html
<my-button @click="handleClick"></my-button>
```

Важное ограничение: работают только те пропсы, которые объявлены в стейте компонента.
Если в стейте компонента нет ключа color — передать color="red" снаружи не получится,
атрибут просто проигнорируется.

```js
// стейт компонента
.state(() => ({ type: 'eye', size: 'md' }))

// ✓ сработает — оба ключа есть в стейте
<icon type="search" size="lg"></icon>

// ✗ не сработает — color нет в стейте компонента
<icon type="search" color="red"></icon>
```

Регистр в именах пропсов не важен: HTML приводит атрибуты к нижнему регистру,
поэтому `:mobileMenu="mobileMenu"` WEX сопоставит с ключом `mobileMenu` в стейте компонента сам.

## Компонент карточки — реальный пример

Сделаем компонент карточки товара, который можно переиспользовать в каталоге:
```js
const productCard = $(`
    <template>
        <div class="card">
            <img w-src="image" alt="Фото">
            <h3>{{ name }}</h3>
            <p>{{ price }} ₽</p>
            <button class="buy-btn">Купить</button>
        </div>
    </template>
`)
  .state(() => ({
      name: '',
      price: 0,
      image: '',
  }))
  .method('buy', state => function(e) {
      alert(`Добавлено в корзину: ${state.name}`)
  })
  .on('click', '.buy-btn', function(state) {
      this.fn('buy')(state)
  })

component('product-card', productCard)
```

Используем в шаблоне через w-for:
```html
<template id="catalog">
    <div class="catalog">
        <product-card
            w-for="item in products traceby item.id"
            :name="item.name"
            :price="item.price"
            :image="item.image">
        </product-card>
    </div>
</template>

<script>
    $('#catalog')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   price: 45,  image: '/img/bread.jpg'  },
              { id: 2, name: 'Молоко', price: 89,  image: '/img/milk.jpg'   },
              { id: 3, name: 'Сыр',    price: 320, image: '/img/cheese.jpg' },
          ]
      })
      .mount()
</script>
```
Три карточки — три независимых компонента, каждый со своим стейтом.

## Эмиттер — компонент говорит с родителем

Пока что данные шли только в одну сторону: родитель передаёт пропсы — компонент
их отображает. Но что если компонент хочет сообщить родителю что что-то произошло?
Для этого есть `emit`.

Представьте компонент-счётчик, который должен уведомлять родителя об изменении значения:
```js
const counter = $(`
    <template>
        <button class="minus-btn">−</button>
        <span>{{ count }}</span>
        <button class="plus-btn">+</button>
    </template>
`)
  .state(() => ({ count: 0 }))
  .on('click', '.plus-btn', state => function() {
      state.count++
      this.emit('change', state.count) // ← сообщаем родителю
  })
  .on('click', '.minus-btn', state => function() {
      state.count--
      this.emit('change', state.count) // ← сообщаем родителю
  })

component('counter', counter)
```
Родитель подписывается через `@change` и регистрирует обработчик через `.fn()`:
```html
<template id="app">
    <counter @change="onCountChange"></counter>
    <p>Родитель знает: {{ total }}</p>
</template>

<script>
    $('#app')
      .state({ total: 0 })
      .method('onCountChange', state => function(newCount) {
          state.total = newCount
      })
      .mount()
</script>
```
Компонент живёт своей жизнью внутри, но в нужный момент «кричит наружу»
через `emit` — родитель слышит и реагирует.

## Локальный компонент vs глобальный

Если компонент нужен только в одном конкретном шаблоне — регистрируйте его
локально через `.component()` прямо на вью. Если нужен по всему приложению —
регистрируйте глобально через `component()` из импорта:

```js
// Глобально — доступен везде
const { component } = window.jqvm
component('my-icon', icon)

// Локально — только для этого шаблона
$('#app')
  .state({ ... })
  .component('my-icon', icon) // ← метод самого вью
  .mount()
```

Локальный компонент виден только в том шаблоне, на котором вы его зарегистрировали.
Дочерние компоненты его не наследуют: если иконка нужна внутри карточки,
регистрируйте её глобально или повторите `.component()` на самой карточке.

# Компоненты в отдельных файлах

## Загружаемые компоненты по URL'у

Когда компонентов становится много, держать их в одном JS-файле неудобно.
Каждому можно отвести свой HTML-файл — и подключать по ссылке.

Пример готового компонента `Button.html`:
```html
<template>
    <slot></slot>
    <br>
    <button class="btn">
        {{ label }}: {{ count }}
    </button>
</template>

<script type="module">
    export default ($component) => $component
        .state({
            label: 'Кликов',
            count: 0
        })
        .method('buy', state => () => {
            state.count++
        })
        .on('click', '.btn', function (state) {
            return this.method('buy')(state)
        })
</script>
```
Как видите, ничего сложного. Разница от обычного кода в
`<script type="module">` и вместо обычной инициализации
мы пишем `export default ($component) => $component`.

Если компоненту не нужна логика, `<script>` можно вообще не писать:
достаточно одного `<template>`, и WEX сделает из него компонент без стейта.

Вызов компонента внутри ДРУГОГО файла `Index.html`:
```html
<template id="component-test">
    <my-button>Welcome!</my-button>
</template>

<script>
    $('#component-test')
        .state()
        .component('my-button', 'button.html')
        .mount()
</script>
```
Как видим, ничего сложного. Указываем имя компонента и его ссылку
прямую или относительную - `.component('my-button', 'button.html')`.

Всё что вы напишете между тегами (`Welcome!` в примере выше) попадёт в то место,
где в шаблоне компонента стоит `<slot></slot>`. Так можно передавать в компонент
не только значения, но и целые куски разметки.

Пока файл скачивается, на месте компонента пусто. Как только он готов,
WEX перерисует родителя сам, ничего делать не нужно.

## Ленивые компоненты по URL'у

Обычный компонент по ссылке начинает скачиваться сразу, как только вы его зарегистрировали:

```js
.component('Article', 'Components/Article.html')
```

Если страница «Статья» открывается не у каждого посетителя, это лишний трафик.
Третьим аргументом можно сказать «не торопись»:

```js
.component('Article', 'Components/Article.html', { lazy: true })
```

Теперь файл скачается в одном из двух случаев:

- тег `<Article>` впервые попал в шаблон, который рендерится прямо сейчас
- его заранее прогрела ссылка `<Link>` (см. документацию роутера)

Заметьте: тег внутри скрытого блока `w-route` или `w-if` в шаблон не попадает.
Пока блок скрыт, компонент не грузится — и это именно то, что нужно.

## Что если загрузка не удалась

Сеть на мобильном бывает капризной, поэтому WEX не сдаётся с первой попытки:
он пробует скачать компонент до трёх раз, делая всё более длинные паузы.
Если и это не помогло, в консоли появится ошибка с адресом файла,
а следующий рендер или наведение на ссылку попробует снова. Компонент не «ломается навсегда».

Ещё две ошибки, которые вы можете встретить в консоли:

- `no <template>` — в файле нет тега `<template>`
- `must export default a function returning a view` — в `<script type="module">`
  забыли `export default` или функция не вернула `$component`

# Общий стейт между компонентами

## Синхронизация компонентов между собой общим стейтом

Когда компонентов на странице становится больше одного, возникает естественный
вопрос: а что если им нужно работать с одними и теми же данными?

Представьте корзину на сайте. Счётчик товаров в шапке, список товаров в боковой
панели и итоговая сумма в футере — три разных компонента, но все они должны
знать об одном и том же: что сейчас лежит в корзине. Если каждый хранит свою
копию стейта — они начнут расходиться и показывать разное.

Store — это единый стейт который несколько компонентов разделяют между собой.
Меняется значение в одном месте — все компоненты которые его используют
обновляются одновременно автоматически.

## Как это работает

```js
// Создаём общий стейт — один на всех
const store = shareState({ count: 10 })

// Оба компонента получают один и тот же store вместо своего стейта
const componentA = $('<span>Значение: {{count}}</span>')
  .state(store)

const componentB = $('<div>count: {{count}}</div>')
  .state(store)
```

```html
<template id="app">
    <comp-a></comp-a>
    <comp-b></comp-b>
</template>
```

```js
$('#app').state({})
  .component('comp-a', componentA)
  .component('comp-b', componentB)
  .mount()
```

Оба компонента видят одно и то же count. Если count изменится — оба перерисуются.

## Реальный пример — счётчик корзины

Сделаем кнопку добавления товара и счётчик в шапке — два независимых
компонента которые работают с одними данными:

```js
// Единый источник правды для всей страницы
const cartStore = shareState({
    itemCount: 0,
    total: 0,
})

// Шапка — только показывает
const cartBadge = $(`
    <template>
        <div class="cart-badge">
            🛒 <span>{{ itemCount }}</span>
        </div>
    </template>
`)
  .state(cartStore)

// Кнопка — только добавляет
const addToCart = $(`
    <template>
        <button class="add-btn">Добавить в корзину ({{ itemCount }})</button>
    </template>
`)
  .state(cartStore)
  .on('click', '.add-btn', state => {
      state.itemCount++
  })
```

```html
<template id="app">
    <cart-badge></cart-badge>

    <main>
        <h2>Товар: Хлеб — 45 ₽</h2>
        <add-to-cart></add-to-cart>
    </main>
</template>

<script>
    $('#app').state({})
      .component('cart-badge', cartBadge)
      .component('add-to-cart', addToCart)
      .mount()
</script>
```

Нажали кнопку — itemCount вырос на единицу в cartStore — оба компонента мгновенно
перерисовались с новым значением. Никакой передачи данных через пропсы, никаких
событий наверх — просто общий стейт.

## Store + localStorage

Store прекрасно сочетается с механизмом storage который мы разбирали раньше.
Достаточно добавить ключ storage в shareState — и общий стейт автоматически
переживёт перезагрузку страницы:

```js
const cartStore = shareState({
    storage: {
        itemCount: 0,
        total: 0,
    }
})
```

Теперь пользователь добавил товары, закрыл вкладку, вернулся — корзина на месте.
И по-прежнему все компоненты синхронизированы между собой.

## Когда использовать Store, а когда пропсы

Не каждый стейт нужно выносить в Store. Хорошее правило:

Пропсы — когда данные принадлежат родителю и он осознанно передаёт их вниз.
Например, родитель знает имя пользователя и передаёт его в дочерний компонент-приветствие.

Store — когда данные нужны нескольким компонентам которые не знают друг о друге и не имеют
общего родителя. Корзина, авторизация, выбранная тема — всё что является глобальным
состоянием приложения.

```
Локальный стейт    →  данные нужны только этому компоненту
Пропсы             →  родитель осознанно делится данными с ребёнком
Store              →  данные нужны нескольким несвязанным компонентам
```

```
Store это не серебряная пуля — не стоит тащить туда всё подряд.
Если данные нужны только одному компоненту, пусть живут в его локальном стейте.

Store появляется тогда, когда без него начинается неудобная передача данных
через длинные цепочки пропсов или костыльные глобальные переменные.
```

# Асинхронные компоненты

Когда приложение растёт, на одной странице может собраться десяток компонентов.
Если грузить их все сразу — пользователь ждёт пока загрузится всё, даже то что ему
сейчас не нужно. Модальное окно которое откроется только если нажать кнопку, редактор
который появится только в режиме редактирования — зачем тащить их при первой загрузке?

Асинхронный компонент — это компонент который загружается только тогда когда действительно
понадобился. Страница открывается быстро с минимумом кода, а тяжёлые части подгружаются
по требованию в фоне.

Ленивые компоненты по URL'у (`{ lazy: true }`), о которых мы говорили выше, решают ту же задачу
для HTML-файлов. `createAsyncComponent` — более общий инструмент: загрузчик вы пишете сами,
и он может вернуть что угодно, будь то JS-модуль или HTML с вашего бэкенда.

## Простейший случай — ленивая загрузка модуля

Компонент живёт в отдельном JS-файле и загружается только когда страница его запрашивает:
```js
// components/user-card.js — отдельный файл
export default $(`
    <template>
        <div class="user-card">
            <h3>{{ name }}</h3>
            <p>{{ email }}</p>
        </div>
    </template>
`)
  .state(() => ({ name: '', email: '' }))
```
```js
// main.js — основной файл
const { createAsyncComponent } = window.jqvm

$('#app')
  .state({ user: { name: 'Алиса', email: 'alice@astre.ws' } })
  .component(
      'user-card',
      createAsyncComponent(() => import('./components/user-card.js'))
  )
  .mount()
```
```html
<template id="app">
    <user-card :name="user.name" :email="user.email"></user-card>
</template>
```
Браузер загрузит `user-card.js` отдельным запросом — и только тогда когда шаблон
встретит тег `<user-card>`. До этого момента файл не скачивается вовсе.

## Загрузка с индикатором — реальный сценарий

Асинхронная загрузка занимает время, и пользователь должен понимать что что-то происходит.
Для этого у `createAsyncComponent` есть второй аргумент — `callback` который вызывается когда
компонент загрузился:
```html
<template id="app">
    <div w-if="!!loading" class="spinner">
        Загружаем редактор...
    </div>
    <rich-editor w-if="!loading"></rich-editor>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({ loading: true })
        .component(
            'rich-editor',
            createAsyncComponent(
                // loader — как загрузить компонент
                () => import('./components/rich-editor.js'),

                // callback — что сделать когда загрузился
                function() {
                    this.update({ loading: false })
                }
            )
        )
        .mount()
</script>
```
Пользователь видит спиннер пока компонент грузится. Как только загрузка завершилась
— loading становится false, спиннер исчезает, редактор появляется.

## Загрузка HTML с сервера

Компонент не обязательно должен быть JS-модулем. Можно загрузить HTML прямо с сервера
через Ajax — удобно когда шаблоны живут на бэкенде:

```js
$('#app')
  .state({ loading: true })
  .component(
      'product-table',
      createAsyncComponent(
          // загружаем HTML через jQuery Ajax
          () => $.get('/components/product-table.html')
            .then((html) => {
                return $(html).vm(() => ({
                    products: [],
                    sortBy: 'name',
                }))
            }),

          function() {
              this.update({ loading: false })
          }
      )
  )
  .mount()
```

Сервер отдаёт кусок HTML, WEX оборачивает его в вью с нужным стейтом — и компонент готов.
Это особенно хорошо сочетается с PHP и Blade: шаблоны хранятся на сервере,
подгружаются по необходимости, данные приходят реактивно.

## Реальный кейс — тяжёлый редактор по клику

Самый частый сценарий применения — откладывать загрузку тяжёлых компонентов до момента
когда пользователь явно их запросил:
```html
<template id="app">
    <div w-if="!editorOpen">
        <p>{{ previewText }}</p>
        <button class="edit-btn">Редактировать</button>
    </div>

    <div w-if="!!editorOpen">
        <div w-if="!!editorLoading">Загружаем редактор...</div>
        <obsidian-editor w-if="!editorLoading"></obsidian-editor>
        <button class="cancel-btn">Отмена</button>
    </div>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({
            previewText: 'Нажмите редактировать чтобы изменить текст.',
            editorOpen: false,
            editorLoading: false,
        })
        .component(
            'obsidian-editor',
            createAsyncComponent(
                () => import('./components/obsidian-editor.js'),
                function() {
                    this.update({ editorLoading: false })
                }
            )
        )
        .on('click', '.edit-btn', state => {
            state.editorOpen   = true
            state.editorLoading = true
        })
        .on('click', '.cancel-btn', state => {
            state.editorOpen   = false
            state.editorLoading = false
        })
        .mount()
</script>
```

Пользователь открывает страницу — редактор даже не начинает загружаться.
Нажал «Редактировать» — только тогда браузер идёт за файлом.
Тяжёлые библиотеки не тормозят первую загрузку страницы.

## Какой способ ленивой загрузки выбрать

У WEX теперь два способа не грузить лишнее. Выбор простой:

```
HTML-файл с <template> и <script type="module">  →  .component(name, url, { lazy: true })
JS-модуль, HTML с бэкенда, свой загрузчик         →  createAsyncComponent(...)
Данные внутри списка, комментарии, переписка      →  w-lazy (см. документацию по ленивой загрузке)
```

## Когда использовать асинхронные компоненты

Не каждый компонент нужно делать асинхронным — это усложняет код и добавляет лишний
сетевой запрос. Хорошие кандидаты:

Грузите асинхронно если компонент тяжёлый (редакторы, графики, карты), показывается
не сразу (модалки, табы, аккордеоны) или нужен только части пользователей
(формы редактирования, админские панели).

Грузите сразу если компонент маленький, нужен при первой загрузке или
является частью основного интерфейса который пользователь видит всегда.

```
Маленькая кнопка, иконка           → обычный компонент
Шапка сайта, главное меню          → обычный компонент
Модальное окно                     → async
Текстовый редактор                 → async
Интерактивная карта                → async
Графики и дашборды                 → async
Форма которая открывается по клику → async
```

```
Асинхронные компоненты — это не оптимизация ради оптимизации.
Это инструмент для конкретной задачи: сделать первую загрузку страницы быстрой,
а тяжёлые части подтягивать только тогда когда они действительно нужны.
```

# Под капотом: что WEX делает за вас

## Рекурсивные компоненты

Компонент может вставлять сам себя: комментарии с ответами, дерево меню, вложенные папки.
Чтобы случайная ошибка не повесила вкладку, WEX ограничивает глубину вложенности —
по умолчанию 50 уровней. Дальше компонент не создаётся, в консоль падает ошибка
с цепочкой компонентов, а на месте проблемного элемента появляется атрибут `data-wex-error="max-depth"`.

Если вы видите такую ошибку, значит у рекурсии нет условия выхода.
Остановите её через `w-if`:

```html
<template>
    <div class="comment">
        {{ comment.text }}
        <comment w-for="reply in comment.replies || []" :comment="reply"></comment>
    </div>
</template>
```

## Много компонентов сразу

Когда на странице сотни компонентов (например, полторы тысячи комментариев),
монтировать их все в одном кадре — значит повесить интерфейс. Поэтому WEX создаёт
первые 50 компонентов сразу, а остальные ставит в очередь и монтирует по кадрам,
укладываясь примерно в 10 мс на кадр. Страница остаётся живой, а порядок остаётся
таким же, как в документе.

## Подсказки в консоли

На localhost WEX подсказывает, что пошло не так: проп получил `undefined`,
выражение в `{{ }}` вернуло пустоту, в `w-src` пришло ничего. В каждой подсказке есть
цепочка компонентов (`app › posts › card`), выражение и доступные переменные —
сразу видно, где именно сломалось. На продакшене остаются только настоящие ошибки.

## Вся идея в одной строке

Компоненты в WEX — это те же самые вью, просто вложенные друг в друга.
Всё что умеет обычный шаблон: стейт, директивы, хуки, `w-for`, `w-if` —
всё это работает и внутри компонента. Никакого нового синтаксиса учить не нужно.

# Серверные компоненты и современные парадигмы рендеринга

Прежде чем разбирать архитектуру — нужно понять картину целиком. 
Откуда вообще берётся HTML который видит пользователь, и почему это важно.

## Откуда приходит HTML

Существует три принципиально разных ответа на этот вопрос.

### CSR — Client Side Rendering. 
Сервер отдаёт почти пустую страницу и большой JavaScript-файл. 
Браузер скачивает JS, выполняет его, и только тогда на экране появляется контент. 
Именно так работают React, Vue и Angular по умолчанию. 
Пользователь первые секунды смотрит на белый экран или спиннер. 
Поисковый робот видит то же самое — пустоту — и с трудом индексирует контент.

### SSR — Server Side Rendering. 
Сервер каждый раз при запросе генерирует готовый HTML 
и отдаёт его браузеру. Пользователь видит контент мгновенно. Поисковик получает 
полноценную страницу. PHP с Blade, Ruby on Rails, Django — классические примеры SSR. 
Это не новомодная идея, а то как веб работал изначально.

### SSG — Static Site Generation. 
HTML генерируется один раз заранее — при сборке проекта 
— и раздаётся всем пользователям как статический файл. Максимально быстро, 
но не подходит для динамических данных. Например, кэширование Blade в Laravel.

```
CSR:  Запрос → пустой HTML + JS → браузер рисует → контент
SSR:  Запрос → сервер думает → готовый HTML → контент
SSG:  Сборка → готовый HTML → Запрос → контент (мгновенно)
```

## В чём проблема чистого CSR

Next.js, Nuxt, SvelteKit — все эти фреймворки появились именно потому что 
CSR оказался неудобен для реального бизнеса. Пришлось изобретать 
«серверные компоненты» поверх изначально клиентских фреймворков. 

Получилось сложно: в Next.js нужно явно писать 'use client' чтобы объяснить 
фреймворку что этот компонент интерактивный, а тот — нет. Два режима, 
два способа мышления, много нюансов.

PHP-first подход переворачивает это с головы на ноги. 
По умолчанию всё серверное — SEO из коробки, быстрая загрузка, никакого белого экрана. 
А туда где нужна интерактивность — аккуратно добавляется WEX.

## Серверный компонент vs клиентский компонент

Серверный компонент — это Blade-шаблон, Twig, Jinja или любой другой шаблонизатор. 
Он живёт на сервере, видит базу данных, знает кто авторизован, имеет доступ 
к переменным окружения. Его результат — готовый HTML, который летит в браузер.

Клиентский компонент — это WEX-вью. Он живёт в браузере, реагирует на действия 
пользователя, обновляет интерфейс без перезагрузки страницы.

| Описание                     | Серверный (Blade)  | Клиентский (WEX)        |
|------------------------------|--------------------|-------------------------|
| Где выполняется              | PHP-сервер         | Браузер пользователя    |
| Видит БД                     | ✓ напрямую         | ✗ только через API      |
| Виден поисковикам            | ✓ сразу            | зависит от данных       |
| Реагирует на клики           | ✗                  | ✓                       |
| Обновляется без перезагрузки | ✗                  | ✓                       |
| Хранит стейт                 | ✗                  | ✓                       |

Они не конкуренты — они партнёры. Каждый делает то, что умеет лучше.

## Базовая архитектура — просто

В простейшем случае всё выглядит так: Blade рисует страницу, 
WEX добавляет жизнь туда где она нужна.

```bladehtml
{{-- resources/views/products/index.blade.php --}}

<h1>Каталог товаров</h1>

{{-- Это серверный HTML — поисковик его прочитает --}}
@foreach($products as $product)
    <div class="product-card">
        <h2>@{{ $product->name }}</h2>
        <p>@{{ $product->price }} ₽</p>
    </div>
@endforeach

{{-- А это уже WEX — только для интерактивного фильтра --}}
<template id="filter">
    <input w-bind="query" placeholder="Поиск по каталогу">
    <div w-if="query.length > 0">
        Ищем: {{ query }}
    </div>
</template>

<script>
    $('#filter').state({ query: '' }).mount()
</script>
```

Товары отрендерил PHP — их увидит Google. Поиск с живой фильтрацией 
добавил WEX — пользователь получил интерактивность.

## Масштабная архитектура

Когда WEX-компонент становится сложным — он начинает обрастать кодом. 
Всё в одном `<script>` становится нечитаемо. Именно здесь Blade раскрывается 
как инструмент организации JavaScript-кода.

Посмотрите на пример следующей структуры моего компонента Obsidian:
```
obsidian/
├── bootstrap.blade.php     ← создаёт глобальный объект window.Obsidian
├── state.blade.php         ← описывает начальный стейт
├── factory.blade.php       ← фабрика: собирает вью из частей
├── hooks/
│   ├── mount.blade.php     ← логика при монтировании
│   └── update.blade.php    ← логика при обновлении
└── actions/
    └── fullscreen.blade.php ← конкретные действия
```
Каждый файл — один маленький <script> с одной ответственностью. 
Blade просто склеивает их в нужном порядке через @include. 
Никакого webpack, никакого npm — только PHP и браузер.

### Фабрика собирает готовый компонент из кусков:

```js 
// factory.blade.php
window.Obsidian.init = function(selector, overrides) {
    return $(selector)
        .state(Obsidian.State(overrides))     // ← из state.blade.php
        .on('$mount',  Obsidian.Hooks.mount)  // ← из hooks/mount.blade.php
        .on('$update', Obsidian.Hooks.update) // ← из hooks/update.blade.php
        .on('click', '.toggle-fullscreen-btn', Obsidian.Hooks.toggleFullscreen)
        .mount();
};
```

А использовать его на любой странице теперь одной строкой:
```bladehtml
{{-- любая страница где нужен редактор --}}
<template id="editor-1"></template>

<script>
    Obsidian.init('#editor-1')
</script>
```

Хотите второй редактор с другим начальным контентом — просто передаёте overrides:
```bladehtml
Obsidian.init('#editor-2', {
    storage: { content: 'Начальный текст...' }
})
```

## Когда совмещать, а когда нет

Хорошее правило: если данные нужны поисковику или должны появиться 
мгновенно — это работа сервера. Если данные появляются в ответ 
на действие пользователя — это работа WEX.

Отдавайте серверу:
- каталоги, статьи, карточки товаров — всё что индексируется
- данные из базы которые не меняются без действия пользователя
- авторизацию и права доступа
- начальное состояние страницы

Отдавайте WEX:
- формы и их валидацию
- фильтры, сортировки, поиск
- модальные окна, табы, аккордеоны
- всё что меняется без перезагрузки страницы
- счётчики, корзины, лайки

## Реальные кейсы:
Интернет-магазин — каталог рендерит PHP (SEO), но фильтр по цене и 
добавление в корзину делает WEX (интерактивность).

Блог — статьи отдаёт сервер (поисковик читает полный текст), но форма 
комментариев с live-preview работает через WEX.

Админ-панель — здесь SEO не нужен вовсе, зато нужна богатая интерактивность. 
Blade даёт структуру и авторизацию, WEX берёт на себя весь UI.

## Главная идея

В мире React и Next.js SSR — это дополнение которое нужно специально 
подключать и настраивать. В мире PHP — SSR это просто то как всё 
работает по умолчанию, и WEX добавляется точечно туда где нужна интерактивность.

Это не компромисс и не костыль — это честное разделение труда. 
Сервер делает то в чём он силён, браузер делает то в чём силён он. 
Пользователь получает быструю страницу, поисковик — полноценный контент, 
разработчик — простую и понятную архитектуру без магии.

```
Пример с Obsidian показывает что даже сложный интерактивный компонент 
— редактор с fullscreen-режимом, подсчётом слов и сохранением в localStorage 
— можно построить на этой связке аккуратно и читаемо. Blade организует файлы, 
WEX управляет стейтом, каждый занимается своим делом.
```

# Фильтры

Представьте что в стейте лежит число `1990.5`.
Вывести его напрямую через `{{ price }}` — получите `1990.5`. Но пользователю хочется 
показать `1 990,50 $`. Можно написать функцию форматирования и вызывать 
её везде вручную — но это быстро превращается в повторяющийся код раскиданный 
по всему шаблону.

Фильтр — это функция-форматировщик которая применяется прямо 
в шаблоне через символ `|`. Один раз описали правило преобразования — 
используете везде одной строкой.

```html 
<div>{{ price | number:2 }}</div>
```

```js 
view.filter('number', function(value, fixed) {
    return value.toFixed(fixed)
})
```

Читается как «возьми price и прогони через фильтр number с аргументом 2».

## Реальные кейсы

### Форматирование цены. 

Самый частый случай — привести число к красивому денежному виду:
```html 
<template id="app">
    <p>Цена: {{ price | currency }}</p>
    <p>Скидка: {{ oldPrice | currency }}</p>
</template>

<script>
    $('#app')
        .state({ price: 1990.5, oldPrice: 2500 })
        .filter('currency', function(value) {
            return value.toLocaleString('ru-RU', {
                style: 'currency',
                currency: 'RUB'
            })
        })
        .mount()

    // Выведет: 1 990,50 ₽ и 2 500,00 ₽
</script>
```

### Дата в человекочитаемом виде. 

Из базы данных обычно приходит строка вроде `2024-03-15T10:30:00` — 
пользователю это показывать не стоит:
```html 
<template id="app">
    <div w-for="post in posts traceby post.id">
        <h3>{{ post.title }}</h3>
        <span>{{ post.createdAt | date }}</span>
    </div>
</template>

<script>
    $('#app')
        .state({
            posts: [
                { id: 1, title: 'Первая статья', createdAt: '2024-03-15T10:30:00' },
                { id: 2, title: 'Вторая статья', createdAt: '2024-01-22T08:00:00' },
            ]
        })
        .filter('date', function(value) {
            return new Date(value).toLocaleDateString('ru-RU', {
                day: 'numeric',
                month: 'long',
                year: 'numeric'
            })
        })
        .mount()

    // Выведет: 15 марта 2024 г. и 22 января 2024 г.
</script>
```

### Обрезка длинного текста. 
Для карточек и превью часто нужно ограничить количество символов:
```html 
<template id="app">
    <div w-for="article in articles traceby article.id">
        <h3>{{ article.title }}</h3>
        <p>{{ article.body | truncate:120 }}</p>
    </div>
</template>

<script>
    $('#app')
        .state({ articles: [...] })
        .filter('truncate', function(value, limit) {
            if (value.length <= limit) return value
            return value.slice(0, limit).trimEnd() + '...'
        })
        .mount()
</script>
```

### Множественное число. 
Классическая задача — «1 товар», «2 товара», «5 товаров»:
```html 
<template id="app">
    <p>{{ count }} {{ count | plural:'товар,товара,товаров' }}</p>
</template>

<script>
    $('#app')
        .state({ count: 0 })
        .filter('plural', function(value, words) {
            const [one, few, many] = words.split(',')
            const mod10 = value % 10
            const mod100 = value % 100

            if (mod100 >= 11 && mod100 <= 19) return many
            if (mod10 === 1) return one
            if (mod10 >= 2 && mod10 <= 4) return few
            return many
        })
        .mount()

    // 1 товар, 3 товара, 11 товаров, 21 товар
</script>
```

## Цепочка фильтров

Фильтры можно применять последовательно — результат одного передаётся в следующий:
```html 
<template id="app">
    <p>{{ comment | truncate:80 | uppercase }}</p>
</template>

<script>
    $('#app')
        .state({ comment: 'очень длинный комментарий пользователя...' })
        .filter('truncate', function(value, limit) {
            return value.length > limit ? value.slice(0, limit) + '...' : value
        })
        .filter('uppercase', function(value) {
            return value.toUpperCase()
        })
        .mount()
</script>
```
Сначала обрежется до 80 символов, затем переведётся в верхний регистр.

## Глобальные фильтры

Если фильтр нужен по всему приложению — регистрируйте его глобально 
через импорт, чтобы не повторять в каждом шаблоне:

```js 
const { filter } = window.jqvm

filter('currency', function(value) {
    return value.toLocaleString('ru-RU', {
        style: 'currency',
        currency: 'RUB'
    })
})

filter('date', function(value) {
    return new Date(value).toLocaleDateString('ru-RU')
})

// Теперь {{ price | currency }} и {{ date | date }}
// работают в любом шаблоне на странице
```

## Когда фильтр, а когда вычисление в стейте

Фильтры — для отображения. Они не меняют исходные данные в стейте, 
только форматируют их на лету при выводе. Если вам нужно именно 
изменить данные и работать с ними дальше в логике — 
делайте это в стейте или в обработчике.

```js 
// ✓ Фильтр — только для показа, данные в стейте остаются числом
{{ price | currency }}   // в стейте: 1990.5, на экране: 1 990,50 ₽

// ✓ Вычисление в стейте — когда результат нужен в логике
state.total = state.items.reduce((sum, item) => sum + item.price, 0)
```

Хорошее правило: если задача «показать красиво» — фильтр. 
Если задача «посчитать и использовать» — стейт.

# Встроенный роутер

Прежде чем разбирать API — нужно понять саму идею.

Когда пользователь переходит по ссылке на обычном сайте, браузер загружает новую
страницу целиком. Роутер в WEX перехватывает эту навигацию и говорит браузеру:
«не перезагружай страницу, я сам разберусь что показать». Адресная строка меняется,
кнопка «назад» работает — но страница не перезагружается. Это и есть клиентский роутинг.

Под капотом роутер переписывает нативные `history.pushState` и `history.replaceState`,
слушает `popstate` — и при любом изменении URL уведомляет вью чтобы та перерисовалась
с учётом нового адреса.

А ещё роутер знает, куда пользователь пойдёт дальше. Пока курсор только летит к ссылке,
он уже качает компонент и данные будущей страницы. К моменту клика всё лежит в кэше,
и страница открывается мгновенно. Об этом — в разделе про `<Link>`.

## Подключение
Роутер подключается как плагин через `.plugin()`:
```js
const { createRouter } = window.jqvm

const router = createRouter({
    mode: 'hash', // или 'history'

    // необязательный параметр: именованные маршруты
    // нужны для удобства, генерации ссылок и prefetch
    // формат: имя маршрута и значение
    routes: {
        'home': '/',
        'post.show': {
            path: '/post/{id:\\d+}',
            component: 'Components/Article.html',
            // позже тут будет ваш API
            data: ({ id }) => [`Structures/Post-${id}.json`],
        },
    },
})

$('#app')
  .state()
  .plugin(router)
  .mount()
```

Значение маршрута может быть просто строкой (`'home': '/'`) — тогда это только путь.
Объект нужен, когда вы хотите prefetch: `component` — адрес компонента страницы,
`data` — адреса данных (массив или функция, которая получает параметры пути).

## Два режима работы:
### hash-режим
URL выглядит как site.ru/#/catalog.
Работает везде без настройки сервера.
Хэш-часть никогда не отправляется на сервер, роутер читает её сам.

### history-режим
URL выглядит как site.ru/catalog.
Красиво, но требует настройки сервера чтобы все пути возвращали
один и тот же index.html. На Apache или Nginx это пара строк в конфиге.

## w-route — показать блок для конкретного маршрута
Это директива-аналог `w-if`, но условие — текущий URL а не стейт.
Значение — это шаблон пути, как в Laravel:

```html
<template id="app">
    <nav>
        <a href="#/" w-navigate="push">Главная</a>
        <a href="#/catalog" w-navigate="push">Каталог</a>
        <a href="#/about" w-navigate="push">О нас</a>
    </nav>

    <div w-route="/">
        <h1>Добро пожаловать!</h1>
        <p>Это главная страница.</p>
    </div>

    <div w-route="/catalog">
        <h1>Каталог товаров</h1>
    </div>

    <div w-route="/about">
        <h1>О нас</h1>
    </div>
</template>

<script>
    $('#app').state().mount()
</script>
```

Заметьте: кавычки внутри кавычек больше не нужны. Значение `w-route` — это не выражение,
а строка-шаблон. Старая запись `w-route="'/catalog'"` по-прежнему работает, но писать её незачем.

Блок, чей маршрут не совпал, на странице не появляется вообще.
Всё, что внутри него (`w-if`, компоненты, `$route.params`), даже не вычисляется.

### Синтаксис шаблона

| Запись | Что значит | Пример совпадения |
|--------|------------|-------------------|
| `/post/{id}` | обязательный параметр | `/post/42` |
| `/post/{id?}` | необязательный параметр | `/post` и `/post/42` |
| `/post/{id:\d+}` | параметр с ограничением (регулярка) | `/post/42`, но не `/post/abc` |
| `/files/{path*}` | всё остальное, включая слеши | `/files/a/b/c.txt` |
| `post.show` | имя маршрута из таблицы `routes` | то, что описано в таблице |
| `regex:/^\/a/i` | сырая регулярка | всё, что она пропустит |

Прямо в HTML ограничение пишется с одним слешем: `w-route="/post/{id:\d+}"`.
В JS-строке (в таблице `routes`) слеш нужно удвоить: `'/post/{id:\\d+}'`.

Есть одно ограничение: внутри `{name:regex}` нельзя использовать фигурные скобки,
то есть `\d{2}` не сработает. Пишите `\d\d` или берите `regex:`.

Если подходят сразу несколько маршрутов, побеждает первый из таблицы `routes`,
затем — те, что встретились только в шаблонах.

## w-navigate — умные ссылки
Обычный `<a href>` вызовет полную перезагрузку страницы. `w-navigate` перехватывает клик
и передаёт навигацию роутеру:

```html
<!-- push — добавляет в историю (можно вернуться назад) -->
<a href="#/catalog" w-navigate="push">Каталог</a>

<!-- replace — заменяет текущую запись в истории -->
<a href="#/login" w-navigate="replace">Войти</a>

<!-- back / forward — как кнопки браузера -->
<button w-navigate="back">← Назад</button>
<button w-navigate="forward">Вперёд →</button>

<!-- open — новая вкладка -->
<a href="https://google.com" w-navigate="open">Открыть</a>
```

## Link — ссылка, которая готовит страницу заранее
`w-navigate` просто переходит. `<Link>` умеет больше: он строит адрес по имени маршрута
и начинает загрузку страницы ещё до клика. Под капотом это обычный `<a>`,
поэтому любые ваши классы и атрибуты работают как обычно:

```html
<!-- по имени маршрута и параметрам -->
<Link to="post.show" :params="{ id: 3 }" class="btn btn-primary">
    Читать далее
</Link>

<!-- по готовому пути -->
<Link to="/about" class="link">О нас</Link>

<!-- имя маршрута из выражения -->
<Link :to="item.route" :params="{ id: item.id }">{{ item.title }}</Link>
```

Лишние ключи в `:params` (которых нет в шаблоне пути) уходят в query:
`:params="{ id: 3, page: 2 }"` даст `#/post/3?page=2`.

### Как работает prefetch
Ссылка начинает грузить страницу в трёх случаях:

- курсор задержался на ней больше ~65 мс (быстрый пролёт мимо не считается)
- палец коснулся экрана — на мобилках это `touchstart`
- ссылка получила фокус с клавиатуры

Что именно грузится, зависит от маршрута в таблице `routes`:

- `component` — HTML и JS компонента страницы
- `data` — все адреса данных, их качает `$wire`

Если у маршрута нет ни `component`, ни `data`, ссылка просто ссылка.

Теперь самое важное. Данные ложатся в кэш `$wire`, и первый же `$wire.get()` с тем же
адресом заберёт готовый ответ, а не пойдёт в сеть:

```js
// prefetch по ссылке уже скачал этот адрес
$wire.get('Structures/Post-3.json').to(state.post)  // отработает мгновенно
```

Адрес должен совпадать символ в символ — вместе с query. Кэш хранится 30 секунд и работает
один раз: следующий заход на страницу получит свежие данные. Время жизни меняется
в настройках `$wire`:

```js
const wire = createWire({ prefetchTtl: 60000 })
```

Чтобы компонент не грузился сразу при старте приложения, а только когда он нужен
(или когда сработал prefetch), помечайте его ленивым:

```js
.component('Article', 'Components/Article.html', { lazy: true })
```

Подробнее — в разделе про ленивую загрузку.

## Параметры пути
Параметры из шаблона `/post/{id}` читаются через `$route.params`:

```html
<div w-route="post.show">
    <Article w-if="posts[$route.params.id]"
             :article="posts[$route.params.id]"></Article>
</div>
```

Значения всегда строки. Если нужно число — приводите сами: `parseInt($route.params.id)`.

Для `regex:` параметры нумеруются по порядку групп. Именованных групп нет:

```html
<div w-route="regex:/^\/product\/(\d+)\/(.+)$/">
    <p>ID: {{ $route.params[0] }}, название: {{ $route.params[1] }}</p>
</div>
```

Что ещё есть в `$route`:

| Поле | Что внутри |
|------|-----------|
| `$route.params` | параметры пути (`{ id: '42' }`) |
| `$route.query` | параметры после `?` (`{ page: '2' }`) |
| `$route.path` | путь без query (`/post/42`) |
| `$route.name` | имя маршрута из таблицы, либо `null` |

## Query-параметры
Всё, что после `?`, роутер читает отдельно — удобно для фильтров, страниц пагинации и сортировки:
```html
<template id="app">
    <div w-route="/catalog">
        <p>Категория: {{ $route.query.category }}</p>
        <p>Страница: {{ $route.query.page }}</p>
        <button class="next-btn">Следующая страница</button>
    </div>
</template>

<script >
    const { createRouter } = window.jqvm
    const router = createRouter({ mode: 'hash' })

    $('#app')
        .state()
        .plugin(router)
        .method('nextPage', function() {
            const { $router } = this
            return () => {
                const { query } = $router.getLocation()
                const current = parseInt(query.page) || 1
                $router.setParams({ page: current + 1 })
            }
        })
        .on('click', '.next-btn', function(state) {
            return this.fn('nextPage')(state)
        })
        .mount()
</script>
```

URL станет `#/catalog?category=shoes&page=2`.
`$route.query` доступен прямо в шаблоне как часть стейта.

Заметьте: раньше `$route.params` хранил query, а `getLocation()` возвращал `params`.
Теперь `params` — это параметры пути, а query переехал в `$route.query` и `getLocation().query`.

## Регулярные выражения в маршрутах

Для гибкого матчинга — например показать один блок для любой страницы
товара — используйте префикс `regex:`:
```html
<!-- Сработает для /product/1, /product/42, /product/anything -->
<div w-route="regex:/^\/product\/.+/">
    <h1>Страница товара</h1>
</div>
```

Флаги пишутся как обычно: `regex:/^\/product\/.+/i`. Голая регулярка без префикса
больше не понимается — путь вроде `/post/new` слишком легко принять за неё по ошибке.

## Ссылки по имени маршрута
Адрес можно собрать и в JS, и не писать его руками:

```js
const { route } = window.jqvm

route('post.show', { id: 5 })            // '#/post/5'  (в history-режиме '/post/5')
route('post.show', { id: 5, page: 2 })   // '#/post/5?page=2'
```

Лишние параметры уходят в query. Если обязательного параметра не хватает, роутер выбросит ошибку
с названием маршрута — молча сломанная ссылка хуже.

Переход из кода:

```js
$router.go('post.show', { id: 5 })              // push
$router.go('post.show', { id: 5 }, 'replace')   // replace
```

## Реакция на смену маршрута

Хук `$route` срабатывает при каждом изменении URL —
удобно для загрузки данных под новый маршрут:
```js
$('#app')
  .vm({ products: [], loading: false })
  .plugin(router)
  .on('$route', (state, url) => {
      if (url === '/catalog') {
          state.loading = true
          $.get('/api/products').then(data => {
              state.products = data
              state.loading = false
          })
      }
  })
  .mount()
```

## Коротко
- `w-route="/post/{id}"` — показать блок; параметры — в `$route.params`
- `regex:...` — сырая регулярка, параметры по индексу
- `<Link to="name" :params="{...}">` — ссылка с prefetch компонента и данных
- `routes` в `createRouter` — имена маршрутов, `component` и `data` для prefetch
- `route(name, params)` — собрать адрес в JS, `$router.go(...)` — перейти
- `$route.query` и `getLocation().query` — параметры после `?`

# Свои директивы.

Директивы — это пользовательские атрибуты которые WEX умеет обрабатывать 
при компиляции шаблона. Если встроенных директив не хватает — вы создаёте свои. 
Нужен атрибут `w-tooltip`, `w-animate`, `w-permission`? — директива именно для этого.

```js 
directive(name, compile, affect)
```

Два этапа обработки: `compile` — на стадии построения виртуального дерева, 
`affect` — когда элемент уже в реальном DOM.

## compile — изменить разметку до вставки в DOM

Вызывается когда WEX встречает ваш атрибут при компиляции шаблона. 
Элемент здесь виртуальный — его ещё нет на странице. Можно менять атрибуты, 
заменять содержимое, возвращать новый HTML.

```js 
const { directive } = window.jqvm

directive('w-link', function($el, attrs) {
    const link = attrs['w-link']
    $el.attr('href', link)
    // ничего не возвращаем — $el используется как есть
})
```
```html 
<template id="app">
    <a w-link="https://example.com">Ссылка</a>
</template>
```

Если вернуть строку — она заменит весь элемент:
```js 
directive('w-badge', function($el, attrs) {
    const count = attrs['w-badge']
    return `<span class="badge">${count}</span>`
    // оригинальный элемент заменён новым
})
```

⚠ `$el` в `compile` — это копия, не реальный DOM-элемент. 
Навешивать события здесь бессмысленно — они не сработают.

## affect — работать с реальным DOM

Вызывается после того как всё дерево скомпилировано и вставлено на страницу. 
Здесь `$el` — настоящий живой элемент. Можно вешать события, инициализировать плагины, читать размеры.
```js 
directive('w-src', null, function($el, attrs) {
    // this.scope.interpolate раскрывает {{ }} внутри значения
    const value = this.scope.interpolate(attrs['w-src'])
    $el.attr('src', value)
})
```
```html 
<img w-src="/images/{{user.avatar}}.jpg">
```
Это исходник встроенного `w-src` — именно так картинка не пытается загрузиться 
по буквальной строке `{{ user.avatar }}` во время компиляции.

## Очистка побочных эффектов

Если в `affect` вы вешаете обработчики или запускаете интервалы — верните функцию-очистку. 
WEX вызовет её перед каждым следующим рендером:

```js 
directive('w-click-outside', null, function($el, attrs) {
    const handler = (e) => {
        if (!$el[0].contains(e.target)) {
            $el.trigger('clickOutside')
        }
    }

    $(document).on('click', handler)

    return () => $(document).off('click', handler)
    // ↑ обязательно — иначе при каждом ре-рендере
    //   будет вешаться новый обработчик
})
```

Пример с инициализацией стороннего плагина:
```js 
directive('w-datepicker', null, function($el, attrs) {
    const picker = $el.datepicker({ format: attrs['w-datepicker'] || 'dd.mm.yyyy' })

    return () => picker.datepicker('destroy')
})
```
```html 
<input w-datepicker="yyyy-mm-dd">
```

## Локальная директива — только для одного шаблона

Глобальная директива через `window.state` работает во всех шаблонах страницы. 
Если директива нужна только в одном месте — регистрируйте её прямо на вью:
```js 
// глобально — доступна везде
const { directive } = window.jqvm
directive('w-highlight', ...)

// локально — только для этого шаблона
$('#app')
  .state({ ... })
  .directive('w-highlight', null, function($el, attrs) {
      $el.css('background', attrs['w-highlight'] || 'yellow')
  })
  .mount()
```

## Встроенные директивы

WEX поставляется с набором готовых директив. 
Все они работают по тем же правилам что описаны выше — просто уже написаны за вас.

- `w-if="!!exp"` — показать или скрыть элемент в зависимости от условия. Элемент физически отсутствует в DOM когда условие ложно.
- `w-for="value,index in data traceby value.id"` — перебор массива. `value,index` без пробела внутри, `,index` необязателен. traceby указывает уникальный ключ для точечного обновления DOM.
- `w-class="{ 'active': !!isActive }"` — добавляет CSS-классы по условию. Принимает объект где ключ это класс, значение — условие.
- `w-bind="keyPath"` — двустороннее связывание для `input`, `select`, `textarea`. Пользователь вводит — стейт обновляется автоматически.
- `w-value="exp"` — одностороннее: из стейта в элемент. Только для `input`, `select`, `textarea`.
- `w-disabled="!!exp"` — блокирует элемент. Работает на `input`, `select`, `textarea`, `button`.
- `w-checked="!!exp"` — управляет `checked` для `input[type=checkbox]` и `input[type=radio]`.
- `w-selected="!!exp"` — управляет `selected` для `select` > `option`.
- `w-src="exp"` — устанавливает `src` у картинки после вставки в DOM. Всегда используйте вместо обычного `src` когда путь динамический.
- `w-on="event:fn"` — привязывает обработчик объявленный через `.fn()`. Работает в паре с ним:
```html 
<button w-on="click:handleSubmit">Отправить</button>
```
```js 
$('#app')
  .state({})
  .fn('handleSubmit', state => function(e) {
      // обработчик
  })
  .mount()
```
- `w-static` — помечает блок как статический. Рендерится один раз и полностью выпадает из цикла перерисовки.
- `w-id="exp"` — присваивает виртуальному узлу стабильный идентификатор для точного патчинга при обновлениях.

# API

## Глобальные функции
После подключения CDN всё доступно через `window.vm`:
```js 
const { component, directive, filter, View, useJQuery } = window.jqvm
```
В проекте с модульной сборкой — через импорт:
```js 
import { component, directive, filter, View, useJQuery } from 'wex'
```
- `component(name, compile, affect)` — зарегистрировать компонент глобально. Доступен во всех шаблонах страницы.
- `directive(name, compile, affect)` — зарегистрировать директиву глобально.
- `filter(name, formatter)` — зарегистрировать фильтр глобально.
- `useJQuery(jQuery)` — передать свою версию jQuery если нужна не та что висит на `window.$`.
- `View` — конструктор вью. Нужен когда хотите проверить принадлежность объекта: `myView instanceof View`.

## Создание вью — $.fn.state
WEX — это jQuery-плагин. Точка входа всегда одна:
```js 
const view = $('#app').state(initState)
```
`.vm()` — полный алиас для `.state()`, работает идентично. 
WEX берёт HTML из выбранного элемента как шаблон и создаёт вью-объект. 
Рекомендуется использовать тег <template> — иначе браузер может отрендерить 
содержимое раньше чем WEX его обработает.

`initState` может быть объектом или функцией возвращающей объект:
```js 
// объект — один на все монтирования, делится между ними
$('#app').state({ title: 'Привет' })

// функция — каждый раз новый независимый объект
$('#app').state(function() {
    return { title: 'Привет' }
})
```
Функция важна когда вы монтируете и демонтируете вью несколько раз — каждый `.mount()` 
получит свежий стейт, а не общий с предыдущим:
```js 
const view = $('#app').state(function init() {
    return { count: 0 }
})

view.mount()
view.unmount()
view.mount() // count снова 0, не сохранился от прошлого монтирования
```
```
Передавать экземпляры классов (new Something()) нельзя — только простые объекты.
```

## Методы вью
Все методы возвращают `view` и поддерживают цепочку.

`.mount(el?)` — вставить вью в DOM. Без аргумента рендерится сразу после 
элемента-шаблона. С аргументом — монтируется внутрь указанного контейнера:
```js 
// после шаблона в DOM
view.mount()

// внутрь конкретного элемента
view.mount('#my-container')
view.mount($('#my-container'))

// или из строки шаблона
$('<template><div>{{title}}</div></template>')
  .vm({ title: 'Привет' })
  .mount('div#app')
```
- `.unmount()` — убрать из DOM, сохранив все подписки. После `unmount()` можно снова вызвать `mount()`.
- `.destroy()` — убрать из DOM и очистить все подписки. После `destroy()` можно монтировать снова, но обработчики нужно навесить заново.
- `.update(nextState?)` — обновить стейт и перерендерить:
```js 
view.update({ title: 'Новый заголовок' }) // смержит как React setState
view.update(true)                          // принудительный ре-рендер без изменений
view.update(state => {                     // функция — полный контроль
    state.count++
})
```
- `.find(selector)` — найти элемент внутри контейнера вью. Аналог `$.fn.find`:
```js 
const $button = view.find('.submit-btn')
```

## Обработчики событий
`.on(event, selector?, action)` — подписаться на событие. 
Главное отличие от jQuery: `action` — это функция которая возвращает другую функцию:
```js 
view.on('click', '.btn', function action(state, ...args) {
    const view = this // доступ к самому вью

    state.count++ // изменение стейта вызовет ре-рендер

    // возвращаем обработчик DOM-события — необязательно
    return function handle(e) {
        const $el = $(this)
        console.log('кликнули на', $el.text())
    }
})
```

Внешняя функция получает стейт и вызывается при каждом событии. 
Внутренняя — это обычный jQuery-обработчик с доступом к `e` и `this`. 
Если DOM-событие не нужно — внутреннюю функцию можно не возвращать.

Асинхронность работает без оговорок:
```js 
.on('click', '.load-btn', state => {
    setTimeout(() => state.items = ['один', 'два'], 1000)
    // через секунду — автоматический ре-рендер
})
``` 
Если изменили экземпляр класса или что-то нереактивное — вызывайте `update()` вручную:
```js 
.on('click', '.btn', state => {
    state.myChart.data = [1, 2, 3] // Chart.js не plain object
    this.update()                  // явный ре-рендер
})
``` 
- `.once(event, selector?, action)` — то же что `.on()` но сработает только один раз. Аналог jQuery `.one()`.
- `.off(event, selector?, action)` — отписаться от события навешенного через `.on()`.

## method — именованные функции
- `.method()` регистрирует функцию на вью по имени. Нужно для w-on директивы и для компонентных событий `@`:
```js 
$('#app')
  .state({ query: '' })
  .method('handleSearch', state => function(e) {
      state.query = $(this).val()
  })
  .method('handleClear', state => () => {
      state.query = ''
  })
  .mount()
```
```html 
<template id="app">
    <input w-on="input:handleSearch">
    <button w-on="click:handleClear">Очистить</button>
    <p>{{ query }}</p>
</template>
```
Получить функцию по имени — вызвать `.fn()` с одним аргументом:
```js 
const fn = view.fn('handleSearch') // вернёт функцию
``` 

## Внутренние события

Хуки жизненного цикла подписываются через тот же `.on()` — просто имя события начинается с `$`:
```js 
$('#app')
  .state({ data: [] })
  .on('$mount', state => {
      // вью появился в DOM — загружаем данные, AJAX-way подход
      $.get('/api/items').then(data => state.data = data) 
      
      // альтернативный современный подход, рекомендуется.
      $wire.get('/api/items').to(state.data);
  })
  .on('$unmount', state => {
      // вью убран — чистим за собой
  })
  .on('$change', state => {
      // стейт изменился
  })
  .on('$render', state => {
      // DOM перерисован
  })
  .mount()
``` 
| Событие   | Когда                       |
|-----------|----------------------------|
| `$mount`  | После вставки в DOM         |
| `$unmount`| После удаления из DOM       |
| `$destroy`| После полного уничтожения   |
| `$change` | При изменении стейта        |
| `$render` | После каждого ре-рендера    |

# Модалки

Из коробки никаких модалок не предусмотрено. Но есть глубокая интеграция с Bootstrap 5.
Для этого мы должны сперва подключить саму библиотеку Bootstrap и дальше начать пользоваться
хелперами Wex.

## 🔌⚡ Подключение.

Здесь нам понадобиться лишь файл стилей и сам бутстрап.

```html 
<link href="https://cdn.jsdelivr.net/npm/bootstrap@5.2.3/dist/css/bootstrap.min.css" rel="stylesheet">
<script src="https://cdn.jsdelivr.net/npm/bootstrap@5.2.3/dist/js/bootstrap.bundle.min.js"></script>
```

После этого не забудьте в сторогой последовательности подключить сперва `jQuery`, а потом и сам `Wex`.

## Механизм.

Есть два принципиально отличных друг от друга механизма работы с модалками в Wex.

### Императивный подход в стиле jQuery Bootstrap 4

Первай механизм самый простой, state-independency (независимый от стейта), он же Bootstrap 4-like,
то есть по образу и подобию сделан как в BS4, пока из него не выпилили jQuery.

```js 
$('#simpleModal').modal('show')
$('#simpleModal').modal('hide')
$('#simpleModal').modal('toggle')
```

То есть мы буквально подключаемся к модалке через jQuery и используем старый синтаксис модалок. 

### Декларативный подход в стиле Wex.

```html 
<template id="app">
    <button class="btn btn-primary" w-modal="myModal">Toggle myModal</button>
</template>

<div id="myModal" class="modal fade" tabindex="-1">
    <div class="modal-dialog"><div class="modal-content">
        <div class="modal-header">
            <h5 class="modal-title">Моя модалка</h5>
            <button type="button" class="btn-close" data-bs-dismiss="modal"></button>
        </div>
        <div class="modal-body">Просто контент</div>
    </div></div>
</div>
```
```js 
$('#app')
    .state({
        modal: {
            myModal: false,
        }
    })
    .mount()
```

Здесь в чём фишка. Идёт глубокая интеграция со стейтом Wex. Флаг `state.modal.myModal`
реактивно отражает состояние модалки. 

Теперь по нюансам обязатальным:
- Кнопка должна иметь специальный тег `w-modal`, а значение этого тега - `id` модалки!
- Стейт обязан иметь вкладку `modal`, это хранилище всех модалок!
- Внутри хранилища модалок Вы обязаны указать айдишник Вашей модалки из `w-modal`! 

### Разница императивного и декларативного подходов

Разница в том, что в декларативном подходе у Вас всего одна строчка кода. 
Вот она. `$('#simpleModal').modal('toggle')`. Вам нет необходимости 
разворачивать целый стейт Wex как во втором случае, но этот самый стейт 
Вы и теряете.

Во втором же случае, идёт плотная интеграция со стейтом, но есть необходимость
заведомо прописать чёткий `state` по правилам, прописать конкретный айдишник
модалке и указать его в `w-modal` кнопки, эту самую модалку открывающей.

## Хуки

| Имя          | Параметры           | Предназначение                   |
|--------------|-------------------|---------------------------------|
| `$modalShown` | `(state, modalKey)` | Вызывается когда показана модалка |
| `$modalHidden` | `(state, modalKey)` | Вызывается когда модалка скрывается |

# Ленивая загрузка

Прежде чем разбирать API — нужно понять саму идею.

Представьте статью с тысячей комментариев. Грузить их все сразу — значит заставить
пользователя ждать ради того, что он, скорее всего, никогда не прочитает. Ленивая загрузка
работает по другому принципу: показываем сколько нужно, а остальное догружаем в тот момент,
когда человек до него докрутил.

В WEX это сделано на двух уровнях:

- **ленивые компоненты** — HTML и JS компонента скачиваются только когда он понадобился
- **ленивые списки** — данные подгружаются порциями по мере прокрутки (`w-lazy`)

Под капотом списки используют нативный `IntersectionObserver`: браузер сам сообщает,
когда край списка появился на экране. Никаких обработчиков `scroll`, никаких лишних
вычислений на каждый кадр.

Базовый пример готовой страницы лежит по пути: `demo/Lazy`.

## Ленивые компоненты

Обычный компонент начинает загружаться сразу, как только вы его зарегистрировали:

```js
.component('Article', 'Components/Article.html')
```

Если страница «Статья» открывается не у каждого посетителя, это лишний трафик.
Третьим аргументом можно сказать «не торопись»:

```js
.component('Article', 'Components/Article.html', { lazy: true })
```

Теперь файл скачается в одном из двух случаев:

- тег `<Article>` впервые попал в шаблон, который рендерится прямо сейчас
- его прогрел prefetch у `<Link>` (см. документацию роутера)

Заметьте: тег внутри скрытого блока `w-route` в шаблон не попадает. Пока маршрут не
активен, компонент не грузится — и это именно то, что нужно.

Пока компонент скачивается, на его месте пусто. Как только он готов, вью перерисуется
сама. Если загрузка упала (сеть, 404), Wex попробует ещё два раза с паузой, а при полном
провале покажет ошибку в консоли и позволит повторить попытку при следующем рендере
или наведении на ссылку.

## w-lazy — подгрузка списка при прокрутке

Директива вешается на контейнер списка. Wex следит за краем этого контейнера
и сообщает вам, когда он оказался рядом с экраном. Что именно подгружать и откуда —
решаете вы, в обработчике события `$lazy`.

### Подгрузка вниз

Классический случай: комментарии, лента, каталог.

```html
<div w-lazy="down">
    <div w-for="c in comments" class="py-3 border-b">
        {{ c.text }}
    </div>
</div>
```

```js
$('#comments')
    .state({ comments: [] })
    .on('$lazy', (state, lazy) => {
        $wire.get(`/api/comments?page=${lazy.page}`)
            .done((items) => {
                if (!items.length) return lazy.end()   // данных больше нет

                items.forEach(item => state.comments.push(item))
                lazy.done()                             // можно грузить следующую порцию
            })
            .fail(() => lazy.fail())                    // повторим через 3 секунды
    })
    .mount()
```

Пустой список тоже работает: край контейнера уже виден, значит, первая порция
запросится сразу после монтирования. Отдельно «стартовую» загрузку писать не нужно.

### Подгрузка вверх

Переписка, как во ВКонтакте: новые сообщения внизу, а старые догружаются, когда
крутишь вверх. Контейнер с `overflow-y: auto` Wex находит сам — это ближайший
прокручиваемый предок.

```html
<div class="h-[70vh] overflow-y-auto">
    <div w-lazy="up">
        <div w-for="m in messages">{{ m.text }}</div>
    </div>
</div>
```

```js
.on('$lazy', (state, lazy) => {
    const oldest = state.messages[0]?.id ?? ''

    $wire.get(`/api/messages?before=${oldest}`)
        .done((older) => {
            if (!older.length) return lazy.end()

            state.messages.unshift(...older)   // старые — в начало списка
            lazy.done()
        })
})
```

Здесь есть неочевидная проблема. Когда сверху добавляются элементы, всё содержимое
сдвигается вниз, и пользователя выбрасывает на другое место переписки. Wex запоминает
позицию прокрутки перед подгрузкой и после перерисовки сам возвращает пользователя
туда, где он был. Вам для этого ничего делать не нужно.

Если чат открывается и сразу должен показать последние сообщения, сначала отрисуйте
начальную порцию и прокрутите контейнер вниз. Иначе край сверху окажется на экране
и первая подгрузка уйдёт без вашего ведома.

## Объект lazy

Обработчик `$lazy` получает вторым аргументом объект с данными и тремя методами:

| Поле | Что это |
|------|---------|
| `lazy.page` | номер подгрузки, начиная с 1 |
| `lazy.offset` | сколько элементов в списке сейчас (удобно для курсорной пагинации) |
| `lazy.direction` | `'down'` или `'up'` |
| `lazy.el` | контейнер списка |
| `lazy.done()` | порция добавлена, можно грузить следующую |
| `lazy.end()` | данные закончились, подгрузка больше не нужна |
| `lazy.fail(ms)` | ошибка: подождать (по умолчанию 3000 мс) и попробовать снова |

Главное правило: **`lazy.done()` вызывается после записи в state**, а не до.
Пока вы не вызвали `done()`, `end()` или `fail()`, новые запросы не стартуют —
поэтому один и тот же запрос не уйдёт дважды, сколько бы пользователь ни крутил.

## Настройка директивы

Атрибуты на контейнере:

```html
<div w-lazy="down"
     w-lazy-margin="400px"
     w-lazy-root="#feed"
     w-lazy-key="query">
```

- `w-lazy-margin` — за сколько пикселей до края начинать подгрузку. По умолчанию `200px`:
  данные приходят раньше, чем пользователь долистает до конца, и он не видит паузы.
- `w-lazy-root` — CSS-селектор прокручиваемого контейнера. Нужен, только если автоопределение
  не подходит. Без него Wex берёт ближайший прокручиваемый предок или окно браузера.
- `w-lazy-key` — выражение, при смене которого список начинается заново.

### Сброс списка по ключу

Поиск, фильтр, смена вкладки: пользователь изменил условие, и подгружать нужно
уже другой список с первой страницы. Для этого есть `w-lazy-key`:

```html
<div w-lazy="down" w-lazy-key="query">
    <div w-for="r in results">{{ r.title }}</div>
</div>
```

```js
.state({ query: '', results: [] })
.on('input', '.search', function(state) {
    return (e) => {
        state.query = e.target.value
        state.results = []        // очищаете список вы сами
    }
})
.on('$lazy', (state, lazy) => {
    $wire.get(`/api/search?q=${state.query}&page=${lazy.page}`)
        .done((items) => {
            if (!items.length) return lazy.end()
            state.results.push(...items)
            lazy.done()
        })
})
```

Как только `query` поменялся, счётчик `lazy.page` обнуляется и подгрузка включается снова,
даже если до этого вы вызывали `lazy.end()`. Список при этом Wex не очищает: это ваши данные.

## Настройки по умолчанию

Если хочется поменять поведение для всего сайта, один раз подключите плагин:

```js
const { createLazy } = window.jqvm

$('#app')
  .state()
  .plugin(createLazy({
      margin: '300px',   // отступ до края
      timeout: 15000,    // через сколько мс считать, что done() забыли
  }))
  .mount()
```

Плагин нужен только для настроек. Сама директива `w-lazy` доступна во всех компонентах
сразу, ничего подключать не надо.

## Предохранители

Ленивая загрузка легко превращается в бесконечный цикл запросов, поэтому у Wex есть защита:

- **Забыли вызвать `done()`.** Через `timeout` (15 секунд) подгрузка разблокируется сама.
- **Сервер вернул ошибку.** `lazy.fail()` не даёт долбить сервер: пауза 3 секунды,
  потом ещё одна попытка.
- **Список не растёт.** Если вызвали `done()`, а количество элементов не изменилось,
  после второго такого раза подгрузка остановится, а в консоли появится предупреждение.
  Когда данные кончились, вызывайте `lazy.end()`: так честнее.
- **Контейнер удалён.** Наблюдатель отключается сам, утечек нет.

## Подводные камни

**Контейнер должен содержать сам список.** `w-lazy` смотрит на первый (для `up`) или
последний (для `down`) элемент внутри контейнера. Если рядом лежат посторонние блоки,
выносите список в отдельный `<div>`.

**Элементы с `display: contents`.** Такие элементы не имеют размеров, и браузер не может
сказать, видны ли они. Wex заглядывает внутрь и берёт ближайший настоящий элемент,
так что `w-for` на обёртках работает без дополнительных усилий.

**Прокрутка в Safari.** Для `up` Wex отключает нативную коррекцию прокрутки браузера
(`overflow-anchor`) и возвращает позицию сам, чтобы не было двойного сдвига.
Это одинаково работает и в Chrome, и в Safari.

**Данные приходят пропом.** Если список лежит в родительском компоненте и передаётся
дочернему через `:comments="comments"`, подгрузку лучше вешать там, где живёт state.
Тогда `$lazy` пишет данные напрямую в свой же стейт.

## Коротко
- `.component(name, url, { lazy: true })` — компонент грузится по требованию
- `w-lazy="down"` и `w-lazy="up"` — подгрузка при прокрутке вниз и вверх
- `.on('$lazy', (state, lazy) => ...)` — вы решаете, откуда брать данные
- `lazy.done()` после записи в state, `lazy.end()` когда данные кончились, `lazy.fail()` при ошибке
- `w-lazy-key` — начать список заново при смене условия

# Префетч

Префетч нужен для оптимизации скорости загрузки сайта для UX клиента. 
При наведении мышкой с ПК все данные предзагружаются в стейт.

Пример можете найти по пути: `/demo/Prefetch/`. В этой папке цельно всё показано.

## Декларативный пример
```html 
<template id="app">
    <button id="btn-load">Загрузить список</button>
</template>

<script>
  $('#app').state({items: []}).mount();
</script>
```

## Императивный пример:
```html 
<template id="app">
  <button w-prefetch="https://mysite.loc/data.json" w-to="items">
    Получить данные при наведении и тут же записать их в стейт.
  </button>
</template>

<script>
  $('#app')
      .state({items: []})
      .on('mouseenter', '#btn-load', () => {
          // Делаем префетч при наведении
          $wire.prefetch('./LazyItems.json')
      })
      .on('click', '#btn-load', (state) => {
          // А вот при клике уже загружаем в стейт
          $wire.get('./LazyItems.json').to(state.items)
      })    
      .mount();
</script>
```

# Wysiwyg редактор

Wysiwyg редактор нужен прежде всего для контента и его редактуры. Он идеально
подойдет для админок, форумов, комментариев и любого другого места, где
требуется базовая, несложная разметка.

Пример реализации лежит в `demo/WYSIWYG`

Редактор не имеет зависимостей и состоит из двух плагинов для Wex:

| Файл | Глобал | Что делает | Где нужен |
|------|--------|------------|-----------|
| `wex-doc.js` | `WexDoc` | Рендер JSON → HTML, директива `w-doc` | Везде, где документ нужно показать |
| `wex-editor.js` | `WexEditor` | Сам редактор, парсер DOM → JSON, директива `w-editor` | Только там, где документ редактируют |

Публичным страницам редактор не нужен: читателю достаточно `wex.js` и `wex-doc.js`.

## Пример

Данный пример выведет базовый редактор и сразу же ниже предпросмотр.

```html
<template id="app">
    <div w-editor="post.body"></div>
    <div w-doc="post.body"></div>
</template>

<footer>
    <script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
    <script src="https://cdn.jsdelivr.net/gh/wemmbley/wex@master/dist/wex.min.js"></script>
    
    <!-- Подключаем только если хотим отрендерить страницу -->
    <script src="https://cdn.jsdelivr.net/gh/wemmbley/wex@master/dist/wex-doc.js"></script>
    
    <!-- Подключаем только если хотим редактировать -->
    <script src="https://cdn.jsdelivr.net/gh/wemmbley/wex@master/dist/wex-editor.js"></script>
    
    <script>
        const { createEditor, HotKeys } = WexEditor

        $('#app')
            .state({ post: { body: null } })
            .plugin(createEditor({ 
                modules: [HotKeys],
                debounce: 0, // мс паузы в наборе; 0 = записывать в state в ближайшем кадре
            }))
            .mount()
    </script>
</footer>
```

Если хочешь стартовать с готового текста, подставь документ вместо null:

```js 
.state({ post: { body: {
    root: { type: 'root', children: [
        { type: 'heading', tag: 'h1', children: [{ type: 'text', text: 'Заголовок', format: [] }] },
        { type: 'paragraph', children: [{ type: 'text', text: 'Текст', format: [] }] },
    ] }
} } })
```

### Порядок подключения

Порядок скриптов важен: директивы `w-doc` и `w-editor` регистрируются при загрузке файла,
а view должен создаваться уже после этого.

1. `jquery`
2. `wex.js`
3. `wex-doc.js`
4. `wex-editor.js`

`.plugin(createEditor(...))` вызывается цепочкой от `.state()` и **до** `.mount()`:
настройки плагина читаются в момент монтирования.

## Как это работает

- Документ лежит в state Wex (в примере `post.body`) в виде обычного JSON.
- `w-editor="post.body"` рисует редактор. Значение атрибута это **путь** в state,
  а не выражение: редактор записывает в него документ через `assign`.
  Объект `post` в state должен существовать, поле `body` может быть `null`.
- `w-doc="post.body"` выводит документ в HTML. Менять его можно из любого места,
  вывод перерисуется сам.
- Редактор держит рабочую копию в DOM (иначе каждый символ сбрасывал бы каретку).
  Изменения уходят в state с паузой `debounce`, а из state документ подтягивается обратно,
  только если его изменили снаружи (например, загрузили с сервера). В этом случае
  содержимое редактора заменяется целиком и каретка сбрасывается.
- Элемент `<div w-editor>` и `<div w-doc>` в шаблоне должны быть пустыми: Wex не будет
  трогать их содержимое при перерисовке.

## Настройки

Передаются в `createEditor({...})`:

| Опция | По умолчанию | Описание |
|-------|--------------|----------|
| `toolbar` | см. ниже | Массив имён пунктов, `'\|'` это разделитель. Можно вставлять объекты (свои пункты) |
| `modules` | `[]` | Классы модулей, например `[HotKeys]` |
| `placeholder` | `'Начните писать…'` | Подсказка в пустом редакторе |
| `debounce` | `0` | Пауза в мс между набором и записью в state. `0` = в ближайшем кадре. Потеря фокуса записывает сразу при любом значении |
| `onChange` | `null` | `fn(doc)`, вызывается при каждой записи документа |

Панель по умолчанию:

```js
['undo', 'redo', '|', 'h1', 'h2', 'p', '|',
 'bold', 'italic', 'underline', 'strike', '|',
 'left', 'center', 'right', '|', 'link']
```

> Настройки общие для всех редакторов на странице: `createEditor` сохраняет их один раз,
> последний вызов побеждает. Разные панели у двух редакторов на одной странице пока
> сделать нельзя.

## Пункты панели

| Имя | Действие | Горячая клавиша |
|-----|----------|-----------------|
| `undo` | Отменить | `Ctrl/⌘ + Z` |
| `redo` | Повторить | `Ctrl/⌘ + Shift + Z` |
| `h1` | Заголовок 1 (повторный клик возвращает абзац) | `Ctrl/⌘ + Alt + 1` |
| `h2` | Заголовок 2 (то же) | `Ctrl/⌘ + Alt + 2` |
| `p` | Обычный абзац | `Ctrl/⌘ + Alt + 0` |
| `bold` | Жирный | `Ctrl/⌘ + B` |
| `italic` | Курсив | `Ctrl/⌘ + I` |
| `underline` | Подчёркнутый | `Ctrl/⌘ + U` |
| `strike` | Зачёркнутый | `Ctrl/⌘ + Shift + X` |
| `left` | Выравнивание по левому краю | `Ctrl/⌘ + Shift + L` |
| `center` | По центру | `Ctrl/⌘ + Shift + E` |
| `right` | По правому краю | `Ctrl/⌘ + Shift + R` |
| `justify` | По ширине (в панели по умолчанию нет) | `Ctrl/⌘ + Shift + J` |
| `link` | Ссылка: запрос адреса, повторный клик по ссылке снимает её | `Ctrl/⌘ + K` |

Кнопки подсвечиваются, когда формат применён к тексту под куркором. Клик по кнопке
применяет формат к выделению.

Неизвестное имя в `toolbar` пропускается, в консоль выводится предупреждение
`[WexEditor] неизвестный пункт тулбара`.

## Горячие клавиши

`HotKeys` это отдельный модуль. Не подключил, значит клавиши пунктов панели не работают
(остаются только штатные сочетания браузера). Подключается так:

```js
createEditor({ modules: [HotKeys] })
```

Модуль берёт поле `hotkey` у пунктов панели, поэтому работает и для твоих пунктов.
Формат: модификаторы `mod` (Ctrl или ⌘), `alt`, `shift`, затем клавиша:
`'mod+alt+k'`, `'mod+shift+x'`. Когда `HotKeys` подключён, сочетание показывается в подсказке кнопки.

## Свой пункт панели

Объект прямо в массиве `toolbar`:

```js
createEditor({
  toolbar: [
    'bold', 'italic', '|',
    {
      name: 'clear',                      // необязательно
      title: 'Очистить формат',           // подсказка и aria-label
      icon: '<svg …>…</svg>',             // HTML иконки; без неё выводится label или name
      hotkey: 'mod+alt+c',                // нужен модуль HotKeys
      isActive: ed => false,              // подсветка кнопки, необязательно
      run: ed => ed.exec('removeFormat'), // действие
    },
  ],
  modules: [HotKeys],
})
```

Или зарегистрировать под именем и использовать как встроенный:

```js
WexEditor.Editor.register('clear', { title: 'Очистить формат', run: ed => ed.exec('removeFormat') })

createEditor({ toolbar: ['bold', 'clear'] })
```

В `run(ed)` и `isActive(ed)` приходит объект редактора:

| Метод | Описание |
|-------|----------|
| `ed.exec(cmd, value)` | Выполнить браузерную команду (`bold`, `insertHTML`, `createLink`, `removeFormat` и т. д.) в редакторе |
| `ed.setBlock('h1')` | Сменить тип блока: `p`, `h1`…`h6` |
| `ed.blockTag()` | Тип блока под курсором: `'p'`, `'h1'`… |
| `ed.alignment()` | Выравнивание блока под курсором |
| `ed.closest('A')` | Ближайший элемент с таким тегом над курсором или `null` |
| `ed.saveRange()` / `ed.restoreRange()` | Запомнить и вернуть выделение (нужно, если открываешь окно ввода) |
| `ed.getDoc()` / `ed.setDoc(doc)` | Прочитать документ / загрузить без события `change` |
| `ed.sync()` | Немедленно записать изменения |
| `ed.on('change', fn)` / `ed.off(...)` | События: `change` (в `fn` приходит документ), `destroy` |

После `run` редактор сам синхронизирует документ и обновляет подсветку кнопок.

## Свои модули

`modules` принимает любые классы: редактор вызывает `new Module(editor)` и при удалении
вызывает `destroy()`, если он есть. `HotKeys` написан именно так и может быть примером.

## Формат документа

```js
{
  root: {
    type: 'root',
    children: [ /* блоки */ ]
  }
}
```

### Блоки

| `type` | Поля |
|--------|------|
| `paragraph` | `children`, `align`, `meta` |
| `heading` | `tag` (`h1`…`h6`), `children`, `align`, `meta` |

`align`: `left`, `center`, `right`, `justify` (необязательно).

### Inline-узлы (внутри блоков)

| `type` | Поля |
|--------|------|
| `text` | `text`, `format` (массив) |
| `link` | `url`, `children` (text-узлы) |
| `linebreak` | перенос строки (`Shift + Enter`) |

`format` принимает: `bold`, `italic`, `underline`, `strikethrough`, `code`, `subscript`, `superscript`.
Порядок в массиве не важен.

### Пример

```json
{
  "root": {
    "type": "root",
    "children": [
      {
        "type": "heading",
        "tag": "h1",
        "align": "center",
        "children": [{ "type": "text", "text": "Главный заголовок", "format": [] }]
      },
      {
        "type": "paragraph",
        "children": [
          { "type": "text", "text": "Привет, ", "format": [] },
          { "type": "text", "text": "как дела? ", "format": ["bold", "italic"] },
          { "type": "link", "url": "https://example.com", "children": [
            { "type": "text", "text": "ссылка", "format": ["underline"] }
          ]}
        ]
      }
    ]
  }
}
```

### meta

Необязательное поле на блоке для настроек, нужных только при выводе:

```json
{ "type": "paragraph", "meta": { "classes": ["text-sm", "text-zinc-500"] }, "children": [] }
```

`meta.classes` попадает в атрибут `class` блока, поэтому подходят любые классы Quas.
Редактор такие классы показывает и сохраняет, но интерфейса для их правки пока нет:
задавай их в самом JSON. В классах разрешены только безопасные символы (буквы, цифры и
`- _ : / [ ] . % # ! ( ) ,`), остальное отбрасывается.

> Сейчас редактор сохраняет у блока только `meta.classes`. Другие поля `meta`, а также
> неизвестные ему типы узлов, после правки в редакторе будут потеряны.
> Это важно, когда документы создаются где-то ещё.

## Вывод документа

```html
<div w-doc="post.body"></div>
```

Директива сама ставит класс `wxe-doc` (типографика заголовков, ссылок, кода) и перерисовывает
содержимое при изменении документа. Использовать вместо неё `w-html` нельзя: он чистит
содержимое как SVG и вырежет обычные ссылки.

Текст статьи выводится после интерполяции, поэтому `{{ ... }}` в тексте не вычисляются как выражения.

Без директивы, в обычном JS:

```js
const html = WexDoc.renderDoc(doc) // строка HTML
```

## Безопасность

- Текст всегда экранируется, в документе нет сырого HTML.
- Ссылки пропускаются только `http(s):`, `mailto:`, `tel:` и относительные. `javascript:`
  и подобные отбрасываются при выводе и при вставке.
- Классы из `meta.classes` проверяются по белому списку символов.
- Вставка из буфера проходит через парсер: остаётся только схема документа
  (абзацы, заголовки, ссылки, форматы). Скрипты, стили, iframe, картинки и чужие классы выбрасываются,
  списки превращаются в абзацы. Обычный текст вставляется как текст.

## Миграция старого HTML

```js
const doc = WexEditor.htmlToDoc('<h2>Заголовок</h2><p>Текст <b>жирный</b></p>')
```

Результат такой же, как при вставке из буфера: подходит для переноса старых статей.
Всё, чего нет в схеме (картинки, таблицы, списки, цитаты), будет упрощено до абзацев.

## Оформление

Стили редактора лежат в самом плагине, Quas для них не нужен. Основные классы и переменные:

| Класс | Что это |
|-------|---------|
| `.wxe` | Контейнер редактора |
| `.wxe-bar`, `.wxe-btn`, `.wxe-sep` | Панель, кнопка (`.is-active` когда активна), разделитель |
| `.wxe-body` | Область ввода |
| `.wxe-doc` | Типографика документа (и в редакторе, и в `w-doc`) |

Цвета заданы переменными на `.wxe`: `--wxe-bg`, `--wxe-fg`, `--wxe-border`, `--wxe-bar`,
`--wxe-hover`, `--wxe-active`, `--wxe-muted`. Тёмная тема включается классом `html.dark` (как в Quas).

Стили типографики объявлены через `:where(.wxe-doc)`, поэтому классы из `meta.classes`
всегда перекрывают их.

## Сборка

В `webpack.config.js` ядро и плагины собираются отдельными файлами:

| Файл | Библиотека | Внешние зависимости |
|------|------------|---------------------|
| `dist/wex.js` | `jqvm` | `jquery` |
| `dist/wex-doc.js` | `WexDoc` | `jqvm` |
| `dist/wex-editor.js` | `WexEditor` | `jqvm`, `WexDoc` |

Для каждого есть `.min.js`. Импорты в исходниках (`../wex.js`, `./wex-doc.js`) должны совпадать
с ключами `externals` в конфиге, иначе webpack начнёт вшивать код в плагин вместо того, чтобы брать его из глобала.

Из `src/index.js` должен экспортироваться `report`: он используется в `wex-doc.js`.

Дока собирается отдельно, чтобы не пересобирать её на каждый билд:

```
npm run build        # только код
npm run build:docs   # код + сборка доки
```

## Если что-то не работает

| Ошибка | Причина |
|--------|---------|
| `view is not defined` | `.plugin()` нужно вызывать цепочкой от `.state()`, а не от несуществующей переменной |
| `WexDoc is undefined` / `WexEditor is undefined` | Файл не подключён или стоит в неправильном порядке |
| `jqvm.report is not a function` | В `src/index.js` не экспортирован `report` |
| Редактор пустой и не пишет в state | В `state` нет объекта по пути из `w-editor` (нужно хотя бы `{ post: { body: null } }`) |
| Настройки плагина не применяются | `.plugin()` вызван после `.mount()` |
| Кнопки без горячих клавиш | Не подключён модуль `HotKeys` |

## Ограничения

Это первая версия. Чего пока нет:

- Блоки только верхнего уровня: абзацы и заголовки. Нет списков, цитат, картинок, iframe, таблиц.
  Они будут добавляться отдельными плагинами через `WexDoc.registerNode(type, fn)`
  (вывод) и `Editor.register(name, def)` (панель).
- Форматирование делается через `document.execCommand`. Он считается устаревшим, но работает
  во всех браузерах. Позже его можно заменить собственной моделью без смены формата документа.
- Редактор защищает свой DOM от перерисовки Wex через служебное поле `__jQvmComponent`
  (см. `protect` в `wex-doc.js`). Это опирается на внутренности Wex. Если в ядре появится
  официальная директива «не трогать содержимое», `protect` можно будет убрать.
- Нет интерфейса для правки `meta.classes`.

# Wex DataTable: справочник

Плагин и компонент для Wex в одном файле: таблица с серверной пагинацией, сортировкой, фильтрами и поиском. Визуально аналог DataTable из PrimeVue, стили на Quas, тёмная тема через `dark:`.
Режим один: **серверный**. Таблица ничего не фильтрует и не сортирует сама, она собирает JSON-запрос, отправляет его и рисует ответ.

Пометка `(не проверено)` стоит у того, что написано по коду, но ещё не прогонялось в браузере.

## Быстрый старт

```html
<script>window.Quas = { AutoDarkMode: false };</script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/quas@master/Source/Quas.js"></script>
<script src="https://unpkg.com/jquery@3.7.1/dist/jquery.min.js"></script>          <!-- jQuery раньше Wex -->
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex-datatable.min.js"></script>                                  <!-- после Wex -->

<template id="app">
  <DataTable url="/api/products" title="Products" :columns="columns" @select="onSelect"></DataTable>
</template>

<script>
const dt = createDataTable({ perPageOptions: [10, 25, 50] })

$('#app')
  .state({
    columns: [
      { field: 'id',    label: 'ID',    type: 'number' },
      { field: 'name',  label: 'Name' },
      { field: 'price', label: 'Price', type: 'number' }
    ]
  })
  .method('onSelect', state => function (keys) { console.log(keys) })
  .plugin(dt)
  .mount()
</script>
```

| Принцип | Что значит |
|---|---|
| Плагин и компонент одновременно | `createDataTable()` регистрирует глобальный компонент и возвращает функцию для `.plugin()` |
| Только сервер | Любое изменение сортировки, фильтров, поиска, страницы или размера страницы приводит к новому запросу |
| Глобальные имена | Тег по умолчанию `<DataTable>`, меняется опцией `name`. Теги компонентов требуют явного закрытия |
| Роутер необязателен | Нет `$router`, значит URL не трогается вообще ([см. раздел](#router)) |

## Тег и props

```html
<DataTable url="/api/products" title="Products" :columns="columns" perPage="25" routeKey="p" @select="onSelect"></DataTable>
```

| Prop | Тип | По умолчанию | Описание |
|---|---|---|---|
| `url` | строка | `''` | Адрес, на который уходит запрос |
| `title` | строка | `''` | Заголовок в панели над таблицей |
| `:columns` | массив | `[]` | Описание колонок ([см. раздел](#columns)) |
| `perPage` | число | опция `perPage` | Начальный размер страницы |
| `routeKey` | строка | опция `routeParam` | Ключ страницы в query. Нужен, если на странице несколько таблиц |
| `@select` | событие | нет | Вызывается при выборе строк, получает массив ключей |

Wex принимает только те props, которые уже есть в state компонента. Опечатка в имени тихо игнорируется.
Колонки должны лежать в **начальном** state родителя: читаются один раз при монтировании.

<a id="columns"></a>

## Колонки

```js
{ field: 'status', label: 'Status', type: 'text', renderer: 'StatusBadge', sortable: true, filterable: true }
```

| Поле | По умолчанию | Описание |
|---|---|---|
| `field` | обязателен | Ключ в строке данных. Он же уходит на сервер в `sort`, `filters`, `columns` |
| `label` | `field` | Заголовок |
| `type` | `'text'` | `text`, `number`, `date`, `boolean`. Определяет набор операторов, тип поля ввода и приведение значений |
| `renderer` | нет | Имя зарегистрированного рендерера. Без него выводится значение как текст |
| `sortable` | `true` | `false` убирает сортировку по колонке |
| `filterable` | `true` | `false` убирает иконку фильтра и колонку из списков «Add filter» |
| `virtual` | `false` | Колонка без данных (например, `Actions`). Не уходит в `columns`, не сортируется, не фильтруется |
| `operators` | из опций по `type` | Список операторов именно для этой колонки |
| `caseSensitive` | из опций | Регистрозависимость текстовых операторов для этой колонки |

Колонка `image` с рендерером `Thumb` обычно ставится как `sortable: false, filterable: false`. Колонка действий: `virtual: true`.

<a id="renderers"></a>

## Рендереры ячеек

Рендерер это обычный Wex-компонент. Регистрируется при инициализации: ключ становится и именем тега, и значением `renderer` в колонке.

```js
const StatusBadge = $(`<template><span class="rounded px-2 py-1 text-xs font-medium" w-class="{
  'bg-blue-100 text-blue-900': value==='Pending',
  'bg-green-100 text-green-900': value==='Delivered' }">{{ value }}</span></template>`)
  .state(() => ({ value: '', row: null }))          // value и row обязательны

const dt = createDataTable({ renderers: { StatusBadge } })
// колонка: { field: 'status', renderer: 'StatusBadge' }
```

| Правило | Пояснение |
|---|---|
| `value` и `row` в state | Таблица передаёт `:value` (значение ячейки) и `:row` (копия строки). Без этих ключей в state props будут проигнорированы |
| State функцией | `.state(() => ({...}))`: компонент создаётся много раз |
| Регистрация глобальная | Локальные компоненты не наследуются дочерними, поэтому рендереры ставятся через глобальный `component()` |
| Имя тега | Как в `renderers`. Регистр в HTML не важен, но пишите единообразно |
| Неизвестное имя | Если `renderer` указан, а компонент не зарегистрирован, ячейка останется пустой |
| Значение `undefined` | Для колонок без данных (`virtual`) в `value` приходит `''` |

Рендереры, которым нужны данные строки (кнопки действий), берут их из `row`.

<a id="options"></a>

## Опции createDataTable

Передаются один раз при инициализации плагина.

```js
const dt = createDataTable({
  perPage: 25,
  perPageOptions: [10, 25, 50],
  caseSensitive: false,
  operators: { number: ['equals', 'between', 'greater_than'] },
  response: { total: 'meta.total' }
})
```

| Опция | По умолчанию | Описание |
|---|---|---|
| `name` | `'DataTable'` | Имя тега |
| `perPage` | `15` | Размер страницы по умолчанию |
| `perPageOptions` | `[5, 10, 15, 25, 50]` | Варианты в списке Rows per page |
| `rowKey` | `'id'` | Поле-идентификатор строки: для выбора строк и `traceby`. Нет поля, берётся индекс |
| `routeParam` | `'page'` | Ключ страницы в query роутера |
| `caseSensitive` | `false` | Регистрозависимость текстовых операторов. Переопределяется на колонке |
| `match` | `'all'` | Как комбинировать условия: `all` (И) или `any` (ИЛИ). Уходит в `filters.match` |
| `multiSort` | `true` | Shift+клик добавляет поле к сортировке |
| `renderers` | `{}` | `{ Имя: WexView }` ([см. раздел](#renderers)) |
| `transport` | `$wire.post` | Своя отправка запроса ([см. раздел](#transport)) |
| `operators` | см. [операторы](#operators) | Доступные операторы по типу колонки |
| `operatorLabels` | `{}` | Подписи операторов, например `{ contains: 'содержит' }` |
| `request` | см. [запрос](#request) | Имена ключей запроса |
| `response` | см. [ответ](#response) | Пути к данным в ответе |

Объекты `request`, `response`, `operators`, `operatorLabels` сливаются с умолчаниями на один уровень: меняете один ключ, остальные остаются. Но `operators.number: [...]` заменяет список целиком.

<a id="operators"></a>

## Операторы фильтров

| Тип колонки | Операторы по умолчанию |
|---|---|
| `text` | `equals`, `not_equals`, `contains`, `not_contains`, `starts_with`, `ends_with`, `in`, `not_in`, `is_null`, `is_not_null`, `is_empty`, `is_not_empty` |
| `number` | `equals`, `not_equals`, `greater_than`, `less_than`, `greater_or_equal`, `less_or_equal`, `between`, `not_between`, `in`, `not_in`, `is_null`, `is_not_null` |
| `date` | `equals`, `not_equals`, `greater_than`, `less_than`, `greater_or_equal`, `less_or_equal`, `between`, `not_between`, `is_null`, `is_not_null` |
| `boolean` | `equals`, `not_equals`, `is_null`, `is_not_null` |

Что ожидается в `value`:

| Вид | Операторы | Форма `value` |
|---|---|---|
| Без значения | `is_null`, `is_not_null`, `is_empty`, `is_not_empty` | ключа `value` в условии нет |
| Два значения | `between`, `not_between` | массив ровно из двух элементов. Границы **включительные** |
| Список | `in`, `not_in` | массив. В поле вводится через запятую |
| Одно значение | остальные | скаляр |

`is_null` проверяет `NULL`, `is_empty` проверяет пустую строку `''`: это разные вещи.

Свой набор на колонку:

```js
{ field: 'status', operators: ['equals', 'not_equals', 'in', 'not_in'] }
```

Лишнее убирается через опцию `operators` (на все колонки типа) или `operators` на колонке (только на неё).

<a id="request"></a>

## Протокол запроса

Запрос уходит `POST` с JSON-телом ([транспорт](#transport)).

```json
{
  "page": 5,
  "per_page": 20,
  "sort": [
    { "field": "name", "dir": "asc" },
    { "field": "created_at", "dir": "desc" }
  ],
  "search": { "field": null, "value": "almanach" },
  "filters": {
    "match": "all",
    "items": [
      { "field": "title", "operator": "contains", "value": "almanach", "case_sensitive": false },
      { "field": "price", "operator": "between", "value": [1, 10] },
      { "field": "deleted_at", "operator": "is_null" }
    ]
  },
  "columns": ["id", "title", "price"]
}
```

| Ключ | Описание |
|---|---|
| `page`, `per_page` | Номер страницы с 1 и размер страницы |
| `sort` | Массив: порядок элементов это приоритет сортировки. Пустой массив, если сортировки нет |
| `search` | `null` или `{ field, value }`. `field: null` значит «по всем колонкам», список колонок для поиска определяет сервер |
| `filters.match` | `all` или `any` |
| `filters.items` | Условия. На одно поле можно несколько, например `price > 10` и `price < 2` |
| `case_sensitive` | Только у условий по колонкам типа `text` |
| `columns` | Поля, которые нужны клиенту: все колонки, кроме `virtual` |

Значения в `value` приведены по типу колонки: `number` это число, `boolean` это `true/false`, остальное строка (даты в `YYYY-MM-DD`).

Имена ключей меняются опцией `request`:

```js
createDataTable({ request: { perPage: 'limit', filters: 'where' } })
```

Любое изменение сортировки, фильтров, поиска и размера страницы **сбрасывает страницу на первую**.

<a id="response"></a>

## Протокол ответа

Стандарт: ответ Laravel `paginate()` (EloquentCollection).

```json
{
  "current_page": 1,
  "data": [ { "id": 1, "name": "Test one" } ],
  "from": 1,
  "to": 15,
  "last_page": 4,
  "per_page": 15,
  "total": 60
}
```

| Ключ по умолчанию | Что означает |
|---|---|
| `data` | Строки |
| `total` | Всего записей по текущим фильтрам |
| `current_page` | Страница, которую вернул сервер |
| `per_page` | Размер страницы |
| `last_page` | Последняя страница |
| `from`, `to` | Диапазон для надписи Showing … from … results. `null` читается как `0` |

Если сервер вернул другую страницу (например, запрошена 9, а есть 4), таблица принимает `current_page` из ответа.

Другой формат (API Resource с `meta`) настраивается без правки кода, пути пишутся через точку:

```js
createDataTable({
  response: { total: 'meta.total', page: 'meta.current_page', lastPage: 'meta.last_page', from: 'meta.from', to: 'meta.to', perPage: 'meta.per_page' }
})
```

Таблица добавляет к строкам служебные поля `_key` и `_cells`. Имена начинаются с `_`, избегайте их в своих данных.

<a id="transport"></a>

## Транспорт и тестирование без сервера

По умолчанию: `$wire.post(url, body)`.

Свой транспорт получает `(url, body)` и возвращает `jqXHR` или `Promise`:

```js
createDataTable({
  transport: (url, body) => $wire.post(url + '?v=2', body)
})
```

**Фейковый сервер** для разработки: транспорт, который читает статический JSON через `$wire` и сам считает фильтры, сортировку, поиск и пагинацию в формате Laravel `paginate()`.

```js
let cache = null
const loadAll = () => cache || (cache = new Promise(res => $wire.get('./products.json').done(res)))

createDataTable({
  transport: (url, body) => loadAll().then(all => { /* фильтры, сортировка, пагинация */ return result })
})
```

Полная реализация (все операторы, `search`, мультисортировка) лежит в `index.html` демо. В проде опцию `transport` просто убирают. Открывать демо нужно через локальный сервер: с `file://` браузер не даст прочитать `products.json`.

| Нюанс | Пояснение |
|---|---|
| Гонки | Если запросы идут один за другим, применяется только ответ последнего |
| Ошибка | При неудаче строки очищаются, выводится `Failed to load data` |
| Загрузка | Пока идёт запрос, тело таблицы затемняется |

## Сортировка, фильтры, поиск в интерфейсе

| Элемент | Поведение |
|---|---|
| Клик по заголовку | `asc`, затем `desc`, затем сортировка снята |
| Shift + клик | Добавляет поле к текущей сортировке (если `multiSort`). Порядок добавления это приоритет |
| Иконка сортировки | Обе стрелки яркие, если сортировки нет. Активная стрелка яркая, вторая притушена |
| Иконка фильтра в колонке | Открывает панель **под этой колонкой** с уже выбранным полем. Если по колонке есть фильтр, иконка синяя |
| Кнопки справа сверху | Фильтр и поиск: панель открывается под кнопкой |
| Панели | Закрываются крестиком, Cancel или кликом вне панели. Повторный клик по той же иконке тоже закрывает |
| Active filters | Чипсы с условиями и поиском. Крестик убирает условие |
| Оператор | При смене колонки список операторов и тип поля ввода пересчитываются: `number` это числа, `date` это календарь, `boolean` это список true/false |
| Пустое значение | Фильтр с пустым значением (кроме `is_null` и подобных) не применяется |
| Нет данных | Под таблицей выводится `No results` или `Loading…` |

Позиция панели считается от карточки таблицы: левый край под колонкой, зажатый границами карточки. (не проверено на узких экранах)

<a id="router"></a>

## Роутер и номер страницы

Если подключён роутер Wex, страница хранится в query: `#/products?page=5`.

```js
$('#app').state({...}).plugin(createRouter({ mode: 'hash', routes: { home: '/' } })).plugin(dt).mount()
```

| Ситуация | Что происходит |
|---|---|
| Монтирование | Номер страницы читается из `?page=`, иначе 1 |
| Клик по странице | Пишется `setParams({ page })`: добавляется запись в историю |
| Назад/вперёд в браузере | Событие `$route`: если страница в URL отличается, таблица грузит её |
| Сброс на первую страницу | После смены сортировки или фильтра `page=1` тоже пишется в URL |
| Несколько таблиц | У каждой свой `routeKey`, иначе они будут делить один `page` |
| **Роутера нет** | URL не читается и не пишется: доступ к роутеру ленивый, ошибок нет |

Порядок `.plugin(router)` и `.plugin(dt)` не важен. Фильтры и сортировка в URL **не** пишутся.

(не проверено: запись `page=1` в hash-режиме и поведение кнопки «Назад»)

<a id="theme"></a>

## Тёмная тема и Quas

Тема работает по классу `dark` на `<html>`, во всех элементах через `dark:`. Если тема переключается вручную, в Quas нужен `window.Quas = { AutoDarkMode: false }` до подключения `Quas.js` (см. справочник Quas, раздел «Тёмная тема»).

Все классы из набора Quas, ничего дополнительно подключать не нужно: `table`, `table-row`, `table-cell`, `table-header-group`, `table-row-group`, `align-middle`, `even:`, `hover:bg-*/50`, `accent-blue-500`.

**Почему таблица сделана на `div`.** Wex перерисовывает элемент с `w-for`, разбирая его HTML вне контекста таблицы, и браузер выбрасывает теги `<tr>`, `<td>`, `<th>` вместе с атрибутом `w-for`. Поэтому вся таблица построена на `div` с `display: table-*` и ролями `role="table|row|cell|columnheader|rowgroup"`.

| Что | Как |
|---|---|
| Подсветка сортировки, иконка фильтра, текущая страница, затемнение | Готовые строки классов, интерполируются в `class="… {{ … }}"`. Не `w-class` |
| Внешний вид | Рамка, шапка, футер и панели повторяют каркас: кастомизация через классы в шаблоне |

<a id="server"></a>

## Что должен делать сервер

Клиенту доверять нельзя: всё, что пришло в JSON, нужно проверять.

| Правило | Зачем |
|---|---|
| Белый список колонок для `sort`, `filters`, `search`, `columns` | Иначе через `field` можно добраться до любой колонки |
| Белый список операторов **на колонку** | У `boolean` нет смысла в `contains` |
| Приведение типов по колонке | `value` может прийти не того типа |
| Экранирование `%` и `_` в `LIKE` | Иначе `contains` превращается в шаблон |
| Верхний предел `per_page` | Защита от выгрузки всей таблицы |
| `between` включительный, `in` из массива | Формат задан контрактом ([операторы](#operators)) |
| `case_sensitive` учитывать только для текста | В MySQL это зависит от коллации колонки |
| `search.field: null` | Список колонок для глобального поиска задаёт сервер |
| `filters.match` | `all` это `AND`, `any` это `OR` |

<a id="pitfalls"></a>

## Частые ошибки и ограничения

| Симптом | Причина и решение |
|---|---|
| Таблица пустая, колонок нет | `columns` не лежит в начальном state родителя или prop назван не так: props вне state игнорируются |
| Ячейка пустая | `renderer` указан, а компонент не передан в `renderers` |
| Рендерер не получает данные | В его state нет `value` и `row` |
| `<DataTable/>` не работает | Теги компонентов закрываются явно: `<DataTable></DataTable>` |
| Нет сортировки по колонке | `sortable: false` или `virtual: true` |
| Фильтр по колонке недоступен | `filterable: false` или `virtual: true` |
| Не тот оператор в списке | Тип колонки не `text`, смотрите набор для типа или `operators` на колонке |
| Фильтры пропали после перезагрузки | Так задумано: в URL пишется только страница |
| Таблица не показывает `from`/`to` | Ответ не по формату `paginate()`: настройте `response` |
| Строки «прыгают» при загрузке | Нет уникального `rowKey` в данных |
| `w-for` на `tr/td/th` в своей разметке | Теги пропадают, используйте `div` с `display: table-*` |

# Wex DatePicker: справочник

Плагин и два компонента для Wex: `DatePicker` (дата) и `DateTimePicker` (дата и время). Инпут с маской, календарь, выбор месяца и года, стили на Quas, тёмная тема через `dark:`.

Пометка `(не проверено)` стоит у того, что написано по коду, но ещё не прогонялось в браузере. Логика маски, кликов по сегментам, выбора месяца, года и времени проверена тестами на заглушках Wex.

<a id="quickstart"></a>

## Быстрый старт

```html
<script>window.Quas = { AutoDarkMode: false };</script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/quas@master/Source/Quas.js"></script>
<script src="https://unpkg.com/jquery@3.7.1/dist/jquery.min.js"></script>          <!-- jQuery раньше Wex -->
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>
<script src="/dist/wex-datepicker.min.js"></script>                                  <!-- после Wex -->

<template id="app">
  <DatePicker :value="date" @change="onDate"></DatePicker>
  <DateTimePicker :clickableMonth="true" :clickableYear="true" :value="dt" @change="onDt"></DateTimePicker>
</template>

<script>
const dp = createDatePicker()

$('#app')
  .state({ date: '2026-11-12', dt: '2026-11-12 23:32' })
  .method('onDate', state => function (v) { state.date = v })
  .method('onDt', state => function (v) { state.dt = v })
  .plugin(dp)
  .mount()
</script>
```

| Принцип | Что значит |
|---|---|
| Плагин и компоненты | `createDatePicker(options)` регистрирует глобально `DatePicker` и `DateTimePicker` и возвращает функцию для `.plugin()` |
| Значение у родителя | Компонент не хранит «свою» дату насовсем: он показывает prop `value` и сообщает о выборе событием `@change` |
| Теги | Закрываются явно: `<DatePicker></DatePicker>`, не `<DatePicker/>` |

<a id="props"></a>

## Props и события

| Prop | Тип | По умолчанию | Описание |
|---|---|---|---|
| `value` | строка | `''` | Текущее значение ([формат](#value)). Родитель может менять его в любой момент |
| `clickableMonth` | булево | опция (`false`) | Клик по месяцу **в инпуте** открывает выбор месяца |
| `clickableYear` | булево | опция (`false`) | Клик по году **в инпуте** открывает выбор года |
| `placeholder` | строка | из формата | Например `дд/мм/гггг` |
| `format` | строка | из опций | Формат отображения для этого экземпляра |
| `@change` | событие | нет | Получает новое значение (`''` при очистке) |

```html
<DatePicker :clickableMonth="true" :clickableYear="true"></DatePicker>
<DatePicker clickableMonth="true" value="2000-12-22"></DatePicker>
```

Флаги принимают `true` или `'true'`. Wex отдаёт компоненту только props, которые есть в его state, поэтому опечатка в имени тихо игнорируется.
Начальное значение задаётся prop'ом `value`, а не содержимым тега: так компонент не теряет state.

<a id="value"></a>

## Значение и формат

| Компонент | Формат `value` | Пример |
|---|---|---|
| `DatePicker` | `YYYY-MM-DD` | `2026-11-12` |
| `DateTimePicker` | `YYYY-MM-DD HH:mm` | `2026-11-12 23:32` |

Разделитель между датой и временем может быть пробелом или `T`. Пустое значение это `''`. Некорректная строка читается как пустая.
Значение приходит и уходит в ISO-виде, а в инпуте показывается по формату отображения:

| Токен | Что значит |
|---|---|
| `dd` | День, 2 цифры |
| `MM` | Месяц, 2 цифры (заглавные, чтобы не путать с минутами) |
| `yyyy` | Год, 4 цифры |
| `HH` | Часы |
| `mm` | Минуты |

По умолчанию `dd/MM/yyyy` и `dd/MM/yyyy HH:mm`. Меняется в опциях (`formats`) или на экземпляре (`format="dd.MM.yyyy"`). Разделители любые.

Внешнее изменение `value` (родитель присвоил новое значение, например сбросил форму) подхватывается: инпут, календарь и выбранный день обновляются. (не проверено)

<a id="input"></a>

## Ввод в инпут

Инпут с цифровой клавиатурой и маской формата: вводятся только цифры, разделители подставляются сами.

| Ситуация | Что происходит |
|---|---|
| Ввод цифр | `12` показывается как `12`, `123` как `12/3`, `12122000` как `12/12/2000` |
| Лишние символы | Буквы отбрасываются, лишние цифры тоже |
| Дата введена полностью и корректна | Значение сразу меняется, вызывается `@change`, календарь перелистывается на эту дату |
| Дата введена полностью, но невалидна (`31/02/2026`) | Значение не меняется |
| Потеря фокуса | Неполная или невалидная строка откатывается к последнему валидному значению |
| Поле очищено целиком | Значение сбрасывается в `''` |
| Каретка | При правке в середине остаётся на месте (`setSelectionRange`) |

Допустимый год 1000–9999. Вставка из буфера отдельно не обрабатывается.

<a id="clicks"></a>

## Клики: что открывается

Что открывается, зависит от того, **по какой части текста** в инпуте кликнули (определяется по положению каретки).

| Клик | Флаг выключен (по умолчанию) | Флаг включён |
|---|---|---|
| По дню | Весь календарь | Весь календарь |
| По месяцу | Весь календарь | Панель выбора месяца (`clickableMonth`) |
| По году | Весь календарь | Панель выбора года (`clickableYear`) |
| По часам и минутам, по разделителям | Весь календарь | Весь календарь |
| Иконка-стрелка справа | Открывает и закрывает календарь | Так же |

Месяц и год в панели берутся **из текста в инпуте**, даже если дата ещё не введена целиком: `31/03/` покажет выбранным март.
Клики по месяцу и году **в шапке календаря** работают всегда, независимо от флагов.

<a id="panels"></a>

## Календарь и панели

Попап показывает одну панель за раз: календарь, список месяцев или список годов. После выбора пункта списка возвращается календарь.

| Действие | Результат |
|---|---|
| Клик по дню | Значение меняется. `DatePicker` закрывается, `DateTimePicker` остаётся открытым (нужно выбрать время) |
| Стрелки `‹` `›` | Листают отображаемый месяц, значение не меняют |
| Клик по месяцу или году в шапке | Заменяет календарь списком. Выбранный пункт по центру списка |
| Выбор месяца или года в списке | **Значение меняется сразу**: день сохраняется, при необходимости уменьшается (`31` января в феврале станет `28`/`29`). Время сохраняется |
| Выбор месяца или года, значения ещё нет | Меняется только отображаемый месяц, значение не появляется |
| Список годов | Текущий год ±60 по умолчанию. Если значение вне диапазона, диапазон расширяется |
| Escape, клик вне компонента | Закрывает попап |

Календарь всегда показывает 6 недель (42 дня), дни соседних месяцев приглушены.

<a id="datetime"></a>

## DateTimePicker

Рядом с календарём две колонки: часы (0–23) и минуты (0–59). Прокручиваются колесом или свайпом, выбранное значение по центру колонки.

| Нюанс | Пояснение |
|---|---|
| Выбор времени | Меняет значение сразу, если дата уже выбрана |
| Дата ещё не выбрана | Выбор часа и минуты запоминается и применяется вместе с днём. Значение не появляется |
| Колонки при панели месяца или года | Остаются на месте |
| Формат | По умолчанию `dd/MM/yyyy HH:mm`. Ввод вручную требует и дату, и время |

<a id="options"></a>

## Опции createDatePicker

```js
const dp = createDatePicker({
  clickableMonth: true,
  formats: { date: 'dd.MM.yyyy', datetime: 'dd.MM.yyyy HH:mm' },
  weekStart: 0
})
```

| Опция | По умолчанию | Описание |
|---|---|---|
| `clickableMonth` | `false` | Значение по умолчанию для всех компонентов. Prop в теге переопределяет |
| `clickableYear` | `false` | То же для года |
| `formats` | `dd/MM/yyyy`, `dd/MM/yyyy HH:mm` | Форматы отображения (`date`, `datetime`) |
| `tokenLabels` | `дд`, `мм`, `гггг`, `чч`, `мм` | Подписи токенов для placeholder |
| `months` | русские | 12 названий, с января |
| `weekdays` | `Вс … Сб` | 7 подписей **с воскресенья** (порядок `Date.getDay()`) |
| `weekStart` | `1` | Первый день недели: `1` понедельник, `0` воскресенье |
| `locale` | `'ru-RU'` | Только для `aria-label` дней |
| `yearsBefore`, `yearsAfter` | `60` | Диапазон списка годов вокруг текущего года |
| `labels` | русские | Подписи кнопок и панелей: `prevMonth`, `nextMonth`, `toggle`, `pickDate`, `pickDateTime`, `hour`, `minute`, `months`, `years` |

Объекты `formats`, `tokenLabels`, `labels` сливаются с умолчаниями на один уровень, а `months` и `weekdays` заменяются целиком.

<a id="locale"></a>

## Локализация

По умолчанию всё русское. Свой язык задаётся при инициализации:

```js
createDatePicker({
  locale: 'en-US',
  months: ['January', 'February', 'March', 'April', 'May', 'June', 'July', 'August', 'September', 'October', 'November', 'December'],
  weekdays: ['Su', 'Mo', 'Tu', 'We', 'Th', 'Fr', 'Sa'],
  weekStart: 0,
  tokenLabels: { dd: 'dd', MM: 'mm', yyyy: 'yyyy', HH: 'hh', mm: 'mm' },
  labels: { prevMonth: 'Previous month', nextMonth: 'Next month', toggle: 'Open calendar' }
})
```

<a id="position"></a>

## Позиция попапа

| Что | Как |
|---|---|
| По умолчанию | Под инпутом, левый край по левому краю инпута, поверх контента (`absolute`) |
| Нет места снизу | Если снизу меньше места, чем сверху, и попап не помещается, он открывается над инпутом |
| Узкий экран | Максимальная ширина `100vw − 2rem`: колонки времени переносятся под календарь |

Положение считается после рендера (примерно через 50 мс), поэтому при открытии возможно короткое мерцание. (не проверено)
Горизонтальный разворот (если инпут у правого края) не делается.

<a id="theme"></a>

## Quas и тема

Тёмная тема работает через `dark:` (класс `dark` на `<html>`). Если тема переключается вручную, в Quas нужен `window.Quas = { AutoDarkMode: false }` до подключения `Quas.js` (см. справочник Quas, раздел «Тёмная тема»).

| Что | Как |
|---|---|
| Классы | Только Quas: сетка, flex, `snap-*`, `overscroll-contain`, `touch-pan-y`, `w-max`, `max-w-[calc(100vw-2rem)]`, `shadow-[…]` |
| Скрытый скроллбар колонок времени | Quas не умеет `scrollbar-width`, поэтому плагин один раз вставляет `<style id="wex-datepicker-css">` с классом `dp-hide-sb` |
| Динамические классы | Подсветка выбранного дня и пунктов списка собирается в JS и вставляется интерполяцией `class="… {{ cls }}"`, не `w-class` |
| Список для `traceby` | Дни, пункты списков, часы и минуты идут массивами из состояния (по одному циклу, без вложенности) |

<a id="pitfalls"></a>

## Частые ошибки и ограничения

| Симптом | Причина и решение |
|---|---|
| Флаг в теге не действует | Prop не из state: проверьте имя (`clickableMonth`, `clickableYear`). Значение должно быть `true` или `'true'` |
| Клик по месяцу открывает календарь | Флаг выключен (по умолчанию). Включите `:clickableMonth="true"` или опцию при инициализации |
| `@change` не вызывается | Handler не зарегистрирован через `.method('onX', state => function (v) {...})` или значение не изменилось |
| После выбора день в инпуте «поехал» | Выбор месяца или года меняет значение, день зажимается до длины месяца |
| Значение не меняется после ввода | Дата неполная или невалидна (`31/02`): при потере фокуса откатится |
| Не работает `value` в Date-формате с точками | Значение всегда ISO (`2000-12-22`); формат с точками задаётся через `formats` |
| Колонки времени без прокрутки колесом | Нужны `overscroll-contain` и `touch-pan-y` (есть в шаблоне); проверьте, что Quas подключён |
| Пустой `<DatePicker/>` | Теги компонентов закрываются явно |
| Ошибка валидации формы не видна | В v1 компонент не выводит ошибки и не создаёт скрытое поле для отправки формы: решается в Blade отдельно |

<a id="missing"></a>

## Чего нет в v1

| Возможность | Статус |
|---|---|
| `min`, `max`, отключённые дни | Не делали |
| Выбор диапазона дат | Нет |
| Вставка из буфера | Отдельно не обрабатывается |
| Кнопка очистки | Нет: поле очищается вручную |
| Начальное значение из содержимого тега | Нет, только prop `value` |
| Скрытое поле для отправки формы, вывод ошибок Blade | Отложено |
| Горизонтальный разворот попапа | Нет |
| Секунды, 12-часовой формат | Нет |
